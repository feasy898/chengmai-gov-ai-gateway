## 一、结论（先答 M0 要回答的问题）

**问题**：候选通道——本地反代 / 系统代理（CONNECT MITM）/ LD_PRELOAD——哪条对 workbuddy/qoder 等桌面 agent 的出网流量可行？

| 通道 | 对应规划形态 | 本实验判定 | 判据（本机实测，详见 §二） |
|---|---|---|---|
| 本地反代（客户端把 endpoint 指到本机端口） | T1（M1 主形态） | **可行，curl 级证伪通过** | T1/T2/T4：明文回环与 TLS 两路均打通 zhipu 真实上游；请求体改写端到端生效（上游 LLM 真实回显注入标记）；SSE 流式逐帧透传 |
| 系统代理 + 证书信任（CONNECT MITM） | T2（M2 辅形态） | **对服从代理且信任 CA 的客户端可行；CA 信任是硬前提（负例证实）** | T3a：信任 mitmproxy CA 的客户端经 CONNECT 打通且改写生效；T3b：同一客户端不信任 CA → curl exit 60 握手失败 |
| LD_PRELOAD | （规划三形态之外） | **不建议**（论证否决，非实测） | 见 §四.3：覆盖面虚假（Go/Rust/静态链接/自带 TLS 栈绕过）+ 无 CA 问题但维护面大，被 T1/T2 支配 |

**杀死判定**（对照 E1 杀死线「可配类 + env 服从类合计 < 2 个 → T2 降级、T3 提前评估」，`开发规划-v1.md:188`）：**未被杀死**。通道层证伪通过；agent 侧「可配类」已有本机在案证据（zcode 经 `provider.baseURL`、kimi 经 `config.toml base_url`，规划三 a 引用本机 AGENTS.md §七/§八，`开发规划-v1.md:86-90`）+ 本实验的 curl 级通道验证 ≥ 2 条路线成立。**但如实登记**：本实验只完成**通道/协议层**证伪（curl 模拟客户端）；**真实桌面 agent 级矩阵未做**（workbuddy/qoder 本机未安装；zcode 已装未接入，理由见 §四.4），E1 的「10 分钟 HTTPS_PROXY 服从性快测」与 QUIC/pinning 实测均**未执行**，归属 M2 矩阵（规划 §四 M2 本来就是矩阵交付阶段，`开发规划-v1.md:213-229`）。

**推荐 M1 路线**：按规划三 a 执行 **T1 回环 baseURL 直配为主**——本实验给出其工程事实基础：回环明文监听时客户端**零 CA 依赖**（T1）、TLS 终结再建路径畅通（T2）、SSE 透传无损（T4）。T2 的 wrapper + 按运行时 CA 分发为辅路线同样得到证据支持（T3a/T3b）。

## 二、实验与证据

### 2.0 环境与负控

- mitmproxy **12.2.3**，装于 `/tmp/mitmenv`（`python3 -m venv` + `pip install -i https://pypi.tuna.tsinghua.edu.cn/simple mitmproxy`）。
- 上游：zhipu 直连，`eval "$(/home/pan-ding/workspace/agent-tools/llm-env zhipu)"` → `LLM_BASE_URL=https://open.bigmodel.cn/api/coding/paas/v4`（key 不录）。模型 `glm-4-flash`。
- **T0 直连负控**（不经代理）：

```bash
curl -sS "$LLM_BASE_URL/chat/completions" -H "Authorization: Bearer $LLM_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"glm-4-flash","messages":[{"role":"user","content":"你好，请用一句话自我介绍"}]}'
```

  实测回复：`你好，我是一个致力于提供专业解答的人工智能助手。`——**无标记**，`prompt_tokens=12`（无注入）。
- 探针 addon（留档 `anongw_m0_addon.py`）：对所有 JSON POST 在 `messages` 头部插入 system 消息「……你必须原样复述这个标记：`ANONGW_M0_<监听端口>`」；每流写一行 JSONL。若上游回复含标记 ⇒ **改写请求体被上游 LLM 真实收到**（端到端证据，非代理层自证）。
- 反向代理实例：`mitmdump --mode reverse:https://open.bigmodel.cn --listen-host 127.0.0.1 --listen-port 8899`；显式代理实例：`--mode regular --listen-port 8898`。

### 2.1 五组测试结果

| # | 通道假设 | 命令要点 | 实测结果 | 判定 |
|---|---|---|---|---|
| T1 | 反代 8899，客户端**明文 HTTP**（=T1 形态：baseURL 直配、零 CA） | `curl http://127.0.0.1:8899/api/coding/paas/v4/chat/completions` | HTTP 200，回复 `……。ANONGW_M0_8899`，`prompt_tokens=40`（12→40，增量=注入的 system 消息），wall 1.38s | **通过** |
| T2 | 反代 8899，客户端 **TLS + 信任 mitmproxy CA**（=完整 MITM 路径） | `curl https://open.bigmodel.cn:8899/... --resolve open.bigmodel.cn:8899:127.0.0.1 --cacert ~/.mitmproxy/mitmproxy-ca-cert.pem` | HTTP 200，回复 `2⏎ANONGW_M0_8899`，`prompt_tokens=42` | **通过** |
| T3a | **系统代理**（CONNECT MITM）+ 信任 CA（=T2 形态） | `curl -x http://127.0.0.1:8898 --cacert ~/.mitmproxy/mitmproxy-ca-cert.pem $LLM_BASE_URL/chat/completions` | HTTP 200，回复 `蔚蓝⏎ANONGW_M0_8898`，`prompt_tokens=40` | **通过** |
| T3b | 同上**不信任 CA**（负例） | 同 T3a 去掉 `--cacert` | `curl: (60) SSL certificate problem: unable to get local issuer certificate`，exit 60 | **如预期失败** ⇒ CA 信任是硬前提 |
| T4 | 反代 8899 + `"stream":true`（M1 流式前提） | 同 T1 加 stream，`curl -N` | 60 个 `data:` 帧逐块到达、`[DONE]` 正常；帧组装后全文含标记 `ANONGW_M0_8899` | **通过** |

mitmproxy 侧证据（`evidence/m0_e1_channel_20261006/m0_e1_evidence.jsonl`，4 行）：4 流全部 `marker_seen_by_llm=true`；上游主机 `open.bigmodel.cn:443`、上游证书 CN=`*.bigmodel.cn`（证明代理确实向真实上游重建 TLS）；key 仅以 `sha256:d4eee0991175` 指纹出现。

### 2.2 实验过程副产物（对 M1/M2 有直接价值）

1. **SSE 跨帧分片导致裸子串假阴**：标记字符串在 SSE 中被拆进多个 `delta.content` 帧，对原始字节流做 `in` 检索漏检（仪器第一版 `marker_seen_by_llm=false`），帧组装后为真。⇒ 呼应规划三 g「裸 digest 检测面」与 M2 `event-stream` 组帧要求（`开发规划-v1.md:66`）：**泄漏/残留计量必须在重组后的文本上做**，在原始分片上检测会系统性假阴。
2. **mitmproxy 12 API 变更**：`server_conn.certificate` 已改名 `certificate_list`（addon 第一版因此抛错）——M2 若封装 mitmproxy 需按 12.x API。
3. 墙钟时延 1.38–2.87s/请求全部为 LLM 推理主导；**壳层 TTFT 增量未单独测量**（属 E4 延迟预实测的量尺工作，本次未做，不冒充结论）。

## 三、桌面 agent「系统代理 + 证书信任」可行性论证（无 GUI 实测下的收口）

**实测边界（如实）**：本机 `workbuddy`、`qoder` **均未安装**（`which` 与常见安装目录均无）；zcode 3.14.4（Electron）已装但未接入实验（理由 §四.4）。故「桌面 agent 认不认系统代理/信任不信任自建 CA」**没有本实验数据**，以下为工程可行性论证，不是实测结论：

1. **OS 层系统代理**：Windows（WinINET/WinHTTP per-user proxy）、macOS（`networksetup`/SCDynamicStore）、GNOME（`org.gnome.system.proxy`，本机现值 `'none'` 可编程改写）都提供无 GUI 可脚本化的设置面——**设置系统代理本身可行**。
2. **证书信任**：T3b 负例证明不信任即失败；信任面按运行时分发（`REQUESTS_CA_BUNDLE` / `SSL_CERT_FILE` / `NODE_EXTRA_CA_CERTS` 等，规划三 a 已列清单，`开发规划-v1.md:87`）比写系统信任库的行政与安全代价小得多（v1 明确不写系统信任库，规划三 a 被否选项）。
3. **agent 侧三个未知数**（只能实测，登记为 M2 矩阵行）：① 是否读系统代理/env 代理（Electron/Chromium 内嵌渲染层认系统代理，但 Node 主进程出网是否走代理取决于实现，**不可假设**）；② 是否证书固定（pinning 命中 → 进排除名单，规划红线绝不绕过）；③ 是否 QUIC/H3 直连绕过代理（Chromium 系有此风险，需防火墙伴生规则兜底，M5 选项）。E1 的「10 分钟 HTTPS_PROXY 服从性快测」（echo 服务）未做——这是把「论证」变「实测」的最短路径，建议 M1 起步即补。
4. **zcode（Electron+Node）**：Node 运行时支持 `NODE_EXTRA_CA_CERTS` 按运行时注入 CA ⇒ T2 路线对其有标准入口；同时它支持 `provider.baseURL` 直配 ⇒ T1 路线零 CA。两路并存，属「最好接入」类，矩阵预期最优行。

## 四、风险与边界（如实登记）

1. **本报告不构成 E1 全量结论**：只覆盖「通道层」子问题。E1 其余子项（真实 agent 逐个实测、QUIC/pinning、服从性快测）未执行，M0 验收口径「E1–E5 各出一页结论」中本报告只兑现 E1 的通道页。
2. **M0 其余项状态**（本会话未触碰，如实登记）：git 工作区在实验前已归零（`git status` 0 条，步骤 0 冻结在案，最近提交 `8321c57`）；步骤 1 两个 mapper 补丁、E2–E5 实验均未开始。
3. **LD_PRELOAD 否决论证**（论证非实测）：按规划五轨迹的形态排序（透明/注入形态全部靠后，`开发规划-v1.md:92`），LD_PRELOAD 相比 T1/T2 无优势：对静态链接、Go/Rust 自带 TLS 栈、setuid/沙箱进程不生效（覆盖面虚假宣告风险，违规划 1.2-#5「不骗人」原则）；注入崩溃即拖垮宿主 agent；且同样要做内容改写，工程量不低于壳层。**v1 不立项**。
4. **zcode 未接入实验的理由**：其 provider 配置（`~/.zcode/v2/config.json`）为全局配置且**当前自动化会话自身正依赖该 provider 运行**，实验中途改写有打断本会话/破坏工作环境的风险；M0 的 curl 级证伪已覆盖通道问题，agent 级实测按规划归 M1-#2（20 轮真实使用验收，`开发规划-v1.md:207`）。
5. **上游端点差异**：实验上游是 zhipu OpenAI 兼容 `paas/v4`；zcode 实际走 anthropic 兼容 `/api/anthropic`。反代按主机转发与协议无关（T1/T2 已证透传与改写），但**响应侧还原**是协议相关功能（规划三 d：M2 必做 Anthropic）——本实验的请求体改写证据不外推为响应还原已解决。
6. 密钥卫生：key 只经 env 与内存传递；证据 JSONL 经 `grep -F "$LLM_API_KEY"` 与 `grep -oE "Bearer …"` 扫描零明文；`/tmp` 实验进程已全部停止（`ss` 复核 8898/8899 无监听）。

## 五、对 M1 的建议（按证据）

1. **主路线 T1 照规划执行**（回环明文监听 + baseURL 直配）：零 CA、零系统侵入，通道证据齐；壳层直接复用本实验的反代转发 + 请求遍历改写模式。
2. **M1 起步即补 E1 服从性快测**（echo 服务 + 目标 agent 的 HTTPS_PROXY 服从性），把 §三的论证转实测；顺带量壳层 TTFT 增量（E4 量尺，与 M1-#4 共用）。
3. **流式计量从第一行代码就在帧组装后做**（§2.2-1 的教训；与规划三 g 裸 digest 检测面同构）。
4. **T2 wrapper 的 CA 分发清单按运行时逐个验证**，Electron 类优先试 `NODE_EXTRA_CA_CERTS`；pinning/QUIC 一票进排除名单，绝不绕过（规划红线）。
