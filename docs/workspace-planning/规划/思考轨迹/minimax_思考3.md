## 1. 我怎么理解这个问题：缺的不是一个代理，是「会话身份」

用户原话的核心是「**无感**」+「**对商业 agent 也有效**」。我先说一个我自己一开始想错的地方。

我最初的框架是：基线是「显式 API 网关」，用户要「透明代理」，所以差的就是一个 mitmproxy 加一个
SNI 分流，把基线的 `detect→mask→route→forward→restore` 搬进代理里。这个框架我认为**是错的（或者说不完整）**。
理由是往下推一步就会撞墙：

**基线的可逆性完全挂在 `session_id` 上。** `masking/mapper.py:222-224`：
`digest = HMAC(MASK_KEY, f"{session_id}\x1f{type}\x1f{normalized}")`。没有会话号，digest 就不存在，
回写就无从查表。而 `session_id` 从哪来？`gateway/app.py:388-389`：
`client_session = request.headers.get("x-anongw-session-id")` → `session_id = client_session or deps.new_session_id()`。
**是客户端给的，或者网关自己编的。**

在透明代理形态下，这两样都没有。代理在 TLS 中间看到的是「到 api.anthropic.com 的一条连接 + 一个 JSON 体」，
它不知道「这是哪场对话」。OpenAI 协议没有标准 session 头，Anthropic 没有。keep-alive 连接在一轮内复用、
跨轮不可靠。当对话历史被压缩（Claude Code 会 compact）时，任何基于前缀的指纹都会漂移。

所以我认为真正的差集是三件事，代理只是其中最表层的一件：

1. **会话身份**：谁告诉回写层「这个 `〔手机号·9cfd96c0〕` 属于我这张映射表」。
2. **占位符形态的抗改形性**：基线已经被真实模型打过脸了（见 §2.3），商业 agent 只会更狠。
3. **覆盖面承诺**：代理能看见的只是发往 LLM 端点的 HTTP 文本体。文件、终端、其它 socket 全是洞。

而这三件事里，第 1 件有一个我认为**被低估的解法**，它同时把第 2、3 件变简单：

> **把占位符的键从「会话级」改成「值级（安装实例级）」**：
> `digest = HMAC(device_key, type | normalized)`，映射表是一张本机全局字典，不按会话分片。

这样回写层**根本不需要知道会话**——占位符自带身份，它只需要查自己那张表。会话稳定性退化成
「同一个值在本机任何时候都是同一个假值」，这反而是**更强**的隐私属性（跨工具一致 = 跨工具不可区分），
而且把「会话路由」这个难题整个删掉了。代价是基线 docstring `mapper.py:9-10` 明写的那条设计意图
（「跨会话因 session_id 参与摘要 → 不同」）被推翻——即本机不同会话之间的占位符可被关联。
**这是一个真正的产品分叉，我认为必须由人来拍（见 §4.1），不是技术选型。**

顺带一个我自己纠正的判断：我一开始想「用户无感 = 加个 20ms 就够」。读完基线 §2.4/§2.3 之后我不这么想了。
基线的形态是**阻断器**（BLOCK 返回 403、代答文案、AI 生成标识、敏感度路由到政务云）。透明形态下这些
大部分**都不成立**：商业 agent 只认它自己的厂商端点，你没法把它的流量路由到政务云上游；
你中途 BLOCK，用户在 agent 工作流中间看到一个错误——那不是「无感」，那是**显眼**。
所以透明形态严格来说是**更小的功能集**，价值命题从「政务合规网关」变成「本机 LLM 防泄漏」。
把这两者当一个产品做，我怀疑两头都做不好。

## 2. 方案空间的自由探索

### 2.1 判定层：不是三选一，是四层，其中第四层我认为是新的

**层 1｜纯规则。** 我实测它在 chat 尺度是 0.098ms，比「无感」预算低三个数量级，**免费**。
结构化号码召回 1.0000（618/618）【基线转录 §2.1，三族实测一致】。硬伤基线自己承认：
人名只有 4 个演示名 + 姓氏启发 0.5 置信，住址 ADDRESS 规则层零产出【基线 §五#1、§2.1 边界】。
看数据更清楚：`data/cases/rule_cases.jsonl` 我统计了实体分布——PERSON 488、SENSITIVE_ATTR 223、
PHONE_MOBILE 176、**ADDRESS 172**、ID_CARD 138…… 规则层打不过的两类恰好是**量最大的两类**。
规则层的价值是「零漏报 + 零可解释性争议」，不是「抓得全」。

**层 2｜快速决策小模型。** 我必须诚实：**我没有跑过任何小模型，这一条基本全是推断。**
本机具备条件（ORT 1.30 CPU EP、64 核、venv 里已装 torch/transformers/onnxruntime【实测】），
但没有权重可跑。可说的是**形态**：用户说的「类似 JEV 那种，速度极快」——我不确定 JEV 指什么，
若是按「能内联跑的快速小模型」理解，那么**它不能是 guard 形态**（Llama Guard 级 8B，量级完全不对），
**必须是判别/分类形态**（token-classification 出 span，或整段二分类出 bool）。
另外一个具体约束：372 条合成用例里 PERSON 488 + ADDRESS 172 个实例——**这个量训不出可用 NER**，
它只够当 smoke test。而且基线 §六#8 明说所有召回/误报数字都来自合成语料、不能外推真实分布。
**用这份数据训一个模型，它会在评测上完美、生产上撒谎。** 我认为这是本项目最可能的自欺方式。

**层 3｜级联（规则先、模型后）。** 我认为这是唯一同时保住两个数字的设计：规则保住结构化号码的
1.0000 召回，模型只负责补规则打不过的开词表类。但它带来一个基线**今天还没有、换模型后必然出现**的问题：
**重叠 span 仲裁**。`masking/mapper.py:262` 是按 start 降序逐个切片拼接的——两层各自产 span 且重叠时，
拼接结果直接是坏的。必须补一条仲裁规则（规则层优先 / 长 span 优先 / 第三方打分）。
还有一个更隐蔽的契约变更：现在语义层**故意不产 span**（`recognizers/semantic/adapter.py:110-114`，
`raw=""`、`end=len(text)`），正因为无 span 才不必面对重叠、且天然不进 `raw` 表面形式清单
（`gateway/pipeline.py:638` 的 `used_surfaces` 构造）。**把 judge 换成能出 span 的模型不是换实现，
是换契约。** 我一开始以为 `recognizers/ner/adapter.py` 那个恒返回 `[]` 的适配器接上模型就完事了，
读到 `pipeline.py:638` 和 `adapter.py:110-114` 才发现不是。

**层 4｜输出侧验证器（我自己加的，我认为是这里最值钱的一个想法）。**
不是「再加一层找实体」，而是：在**已脱敏**的出站文本上跑一次**只出 bool、不出 span** 的小模型，
回答「这里面还有没有残留原文」。理由：
- 输入已经被规则清过一遍，模型面对的是干净文本，任务退化成**高精度残差检测**——比开词表 NER 容易得多；
- 误报代价极低（只是走更严的路径，不影响用户）；
- 单次前向、无解码，是最便宜的一种模型；
- 它让基线表 B 的「**上游实收 bytes 级零原值**」从「规则自己说自己干净」变成**有独立证据**。
  现在的零原值断言和产生它的规则层是**同一个东西**，不是交叉验证。

**关于挂载点**：`recognizers/semantic/judge.py` 已经是现成的接缝——`LlmJudge` 是个 OpenAI 兼容 HTTP 客户端，
`DEFAULT_TIMEOUT_S = 4.0`。**但它现在的形态跟「快」是反的**：4 秒超时的远程 HTTP 调用。
而且它只在词表零命中时才调一次（`adapter.py:105-108`），是串在主链路上的。
所以「换成快模型」的真实内容是：把一个跨网络的串行调用，换成本地进程内的定长预算调用，并且**超预算即降级**。

### 2.2 部署形态：对商业 agent 的有效性 vs 安装成本

| 形态 | 覆盖的商业 agent | 安装成本 / 障碍 | 我的判断 |
|---|---|---|---|
| **base_url 改写（网关 API 模式）** | Cursor 自定义端点、Cline、Aider、Continue、大部分 SDK 系 | 改一个环境变量，近零 | **这就是基线现在的形态**。用户要的「便宜那 80%」已经有了 |
| **本机显式代理（HTTP_PROXY）** | 尊重代理环境变量的应用 | 同下（仍需 MITM 才能看密文体内） | 与透明代理是**同一个技术赌注**，只是流量发现方式不同 |
| **透明 MITM（自建 CA + SNI/CONNECT 分流）** | 硬编码端点的（Claude Code 走 Anthropic、Codex CLI 走 OpenAI） | **要往 OS 信任库装根证书——特权操作，在政务终端上很可能被策略直接禁止** | 唯一真正满足「对商业 agent 有效」的一条，也是一条行政红线不是技术红线 |
| 浏览器 / IDE 插件 | 仅 UI 内流量 | 要重实现一遍引擎 | 低价值，**除非**插件天然持有会话身份（按标签页 = 按会话），这点反而是优势 |
| SDK 封装 / CLI shim | 所有允许改 base_url 的 | 近零 | **最被低估的一条**：它顺手解决了 §1 的会话身份问题——一个进程 = 一个会话，且它自己构造请求，能可靠注入占位符规则 |

我要说的关键点是：**「商业 agent 有效」和「无感安装」在当前形态下是互斥的。**
透明代理能覆盖硬编码端点，但要装根证书；base_url 改写不碰信任库，但覆盖不了硬编码端点。
**没有第三条无代价的路。** 我认为必须承认这个取舍，而不是假装有个透明方案。

还有一个容易被忽略的成本：MITM 之后 TLS 变成**两段**，多一次握手 + 一次重连。
**不做连接池和 TLS 会话复用，每条新连接会多付一个 RTT（~100-200ms）**——这比整个检测层加起来还贵。

### 2.3 回写层：占位符形态才是产品决策

`masking/mapper.py:49-94` 那一整段容错代码，注释写得很清楚，是被真实模型打出来的：
- 同形括号 `〔→【〖［[`、间隔号 `·→・•‧⋅﹒．.`、反引号/空白/换行插入、hex 大小写与全半角；
- hex 易混字符 `O→0 / I·l→1`（`mapper.py:82`）；
- **模型把括号外的前缀文案挪进括号内**：`主号：〔手机号·9cfd96c0〕` → `〔主号：手机号·9cfd96c0〕`（`mapper.py:57-65`）。

我的判断：**这套启发式堆是在给一个错误的设计打补丁。** 根因是：占位符是一个
**需要模型逐字回显的陌生 token**。而 §2.2 的最后一行正好说明问题——商业 agent 比聊天模型更糟，
它会反复引用上下文、做结构化输出、传工具参数。

三条替代路线：

- **(a) 保持不透明 hex**：安全性最高，改形风险最高。基线现状。
- **(b) 自然语言假值**（`张伟` → `李某`，`13800138000` → `13900000001`）：模型把它当普通文本，**保真度最高**；
  而且**保持下游 agent 的逻辑可用**——一个 agent 要校验身份证格式时，不透明占位符会让它的工具直接崩，
  格式合法的假值不会。这在 agent 场景下我认为是被严重低估的收益。
  **但（b）有一个我自己推出来的真实攻击面**：校验位约束的格式（18 位身份证）若只改末位，
  前缀+生日固定后，未知位只剩约 10² 量级，**远端暴力即可还原**。所以假值必须连**地址码和出生日期一起随机化**，
  否则「保格式」这个卖点直接变成漏洞。手机号 8 位随机 = 10⁸ 空间，没问题。
- **(c) 语义型占位**（`[P7f3a2b1c]` 短 ASCII）：介于两者之间，对英文模型保真度高、对中文模型不如（b）。

**我倾向（b），但这是要靠实验定的事，不是我拍脑袋定的。**

最后一条，也是我觉得最要命的：**查不到表的时候怎么办。** `mapper.py:166-173` 的口径是
「完整括号对但不可还原 → 逐字原样放行」。在**网关**形态下这没问题——用户看得懂，那是审计线索。
在**无感工具**形态下，这意味着用户屏幕上赫然出现 `〔手机号·9cfd96c0〕`，这是**最显眼的失败方式**，
是产品被投诉的第一名。触发条件还特别常见：换台机器、工具重启、用户上一轮没被拦截到、对话被压缩。
`mapper.py:177` 的 `tolerant_placeholder_hits` 就是量这个的正确仪器——**我认为它应该是这个产品的一号指标，
不是检测 F1。** 因为「泄漏到屏幕上」是可见失败，会被发现；「原文出网」是不可见失败，只会在审计时曝光。
两者的发现率差着几个数量级，产品会被前者绑架，但必须按后者设计。

### 2.4 性能预算：我把它写成数字

「无感」不是一个形容词，可以定：
- **TTFT 增量 ≤ 20ms p50 / ≤ 80ms p99**（对上游 LLM 的 300ms–2s TTFT 而言，20ms 是 1-7%，感知不到）；
- **agentic 场景按轮累计**：一个会话 50 轮，20ms/轮 = 1s（可接受），200ms/轮 = 10s（用户会骂「这工具卡」）；
- **流式**：回写不得引入任何额外缓冲。基线 `remap.py:44` 候选缓冲上限 48 字符，我实测 2160 字 / 540 chunk 全程 0.99ms，**回写本身是零成本**，唯一的风险是代理层自己加的 flush 延迟。

对照实测：
- 规则层在 chat 尺度（0.098ms）**远低于预算，可以忽略**；
- 规则层在 50k 字（417ms）【实测】**已经超预算 5 倍**。而基线 `m11` 允许到 15 万字符（§2.8），
  按实测的超线性趋势外推【未测】会到秒级。**这是「无感」目标与商业 agent 大上下文场景之间的第一个硬冲突，
  而且它完全不是模型精度问题，是 `detect.py:340` 一个 O(k²) 的实现问题。** 我认为这是最划算的先修项。

**决策小模型放哪、能不能放：**
- 本机是 64 核 + CPU EP【实测】。一个 6 层 / 384 隐层 的中文 encoder，256 token，单次前向大致在几十 ms 量级
  【未测，纯量级推断】；但用户不会总在 windev-01 上跑，**目标机器可能是 4 核笔记本或 2 核云主机**，
  那里同样的模型就是几百 ms。
- **所以我的结论是：模型层必须能按宿主自适应，或者只做级联的残差位。** 一个把「快」写死在
  「快」上面的架构，在客户机上就不成立了。
- 兜底纪律：模型调用必须有**硬时间预算**（比如 30ms），超预算即回落规则，**绝不阻塞主链路**。
  `judge.py:10-11` 的「judge 故障按词表结果降级、不抛错」是已有的正确纪律，应该原样继承到本地模型上。

## 3. 我认为最可能成功的路线，以及先做什么实验去证伪

**路线 A（信心最高，约 70%）：先把「值级占位符 + 抗改形占位符形态」在现有网关形态里做实，
把商业 agent 支持押在 base_url/SDK 封装形态上，透明代理作为第二阶段。**
理由：这是唯一一个不依赖「装根证书」这个行政放行、且基线已经 90% 覆盖的路。
新增的实质工作是：占位符键去会话化、形态重设计、以及一个抗改形的**计量**。
这个路线的最大优点是**每一步都能用基线现成的验收套件证伪**，不需要先解决任何不可控因素。

**路线 B（中信心，约 45%）：透明 MITM 代理 + SNI 分流。**
唯一真正覆盖硬编码端点的路。但它的成败**不取决于技术**，取决于三件我控制不了的事：
目标环境允不允许装根证书、目标 app 有没有证书固定、ECH/HTTP3 有没有普及。
我把它排在第二位不是因为它难，而是因为它的**第一个障碍是行政的**。

**路线 C（低信心，约 25%）：上小模型。**
我不是说它错，我是说**在 §2.1 的数据量约束被解决之前，它是这个项目里最可能交付一个「看起来很聪明、
实际上撒谎」的东西**。基线 §五#3 已经吃过一次亏——语义层的 11/11 是词表降级面的成绩，
真 judge 只做到单元级验证。**同一个坑不该踩第二次。** 模型应该排在抗改形计量之后。

### 我要做的第一个实验（一个下午，零新代码，产出决定性数据）

**改形率实测。** 目的：回答「不透明占位符在真实模型手里到底能不能活下来」。
用基线已有的真实腿（`100.64.0.7:9004` 的 local-chat-8b，§2.8 U8 三族 PASS）跑 200-500 轮，
**故意逼模型回显占位符**：让它列成表格、放 markdown 表格、加反引号、做代码块、输出 JSON 工具参数、
句中复述、截断复述。每次统计三件事：
1. 占位符被改形的比例；
2. 改形后 `restore_tolerant` 实际救回的比例；
3. **泄漏到用户屏幕的比例**（用 `tolerant_placeholder_hits`，`mapper.py:177`）。

**判据**：若泄漏率 > 0.1%，则不透明 hex 方案在 agent 场景**判死**，直接进入形态 bake-off；
若 < 0.01%，基线现有的容错面就够了，路线 B 的优先级可以往前提。
**这个实验会同时给出形态选择的判据**（把上面三档占位符各跑一遍同样的 prompt），
所以它不是探索性实验，是**收敛性实验**——我认为这就是第一步。

**第二个实验**（半天，证伪路线 B）：mitmproxy 插件只 MITM 一个 host 白名单，
打通一条真实 Claude Code / Cursor 请求。成功标准不是「代码跑通」，是
**「目标机器的 OS 信任库接受我们的 CA，且目标 app 不做证书固定」**。这一步出不来，路线 B 直接归档。

**第三个实验**（小）：在 `detect.py:340` 上做个 `bisect` 原型，把 50k 字从 417ms 压到 30ms 以内。
**如果这一步都做不到，「无感」在大上下文场景就是空话，后面所有精度工作都是在错误的层面上做优化。**

## 4. 风险、我不知道的事、需要人来拍的分叉

**4.1【需拍板·最重要】占位符键：会话级 vs 值级（安装实例级）。**
基线明确选了会话级（`mapper.py:9-10`），理由是可防跨会话关联——在**政务网关**下这是对的。
但在**本机个人工具**下，值级（`HMAC(device_key, type|value)`）换来的是：跨工具/跨轮/跨进程
一致、回写层不需要会话身份、**§1 那个难题整个消失**。代价是本机内跨会话可关联。
**我倾向值级 + 每安装实例独立 key**（换机器/换安装 = 新的、不可关联的命名空间，隐私属性不降反升）。
但这推翻了基线的既有设计意图，**不是我该单方面定的**。

**4.2【需拍板】透明形态下还保不保留路由与审计？**
商业 agent 不会把流量发给你的政务云上游，所以「敏感度路由」在透明形态下**物理上不成立**；
「中途 BLOCK」在无感形态下**违反产品定义**。所以我判断透明形态必然是「只变换、不阻断、不路由」的**子集产品**。
那它到底是「政务网关的一个新入口」还是「另一个产品」？**这决定定位、决定客户、决定要不要保留合规叙事。**
我怀疑混着做会两头落空。

**4.3【需拍板】占位符形态：不透明 hex / 自然语言假值 / 短 ASCII。**
我倾向自然语言假值（§2.3 的两条理由 + 附带发现：**身份证类假值必须连地址码和生日一起随机化，
否则 10² 暴力可还原**）。但要实验定，并且要考虑一个我不确定的点：自然语言假值会让远端
**看出这里被脱敏了**（一串"李某某/13900000001"是不自然的），不透明 hex 至少形状上更中性。
这个权衡我判断不了。

**4.4【需拍板】查不到映射时的兜底：原样放行 / 静默丢弃 / 换中性表述。**
基线口径是原样放行（`mapper.py:166-173`），在无感产品里这是**最显眼的失败**。我倾向
「静默降级为中性表述」，但这会**悄悄改变用户看到的内容**——在政务场景这是不可接受的，
在个人工具里可能可以。**分叉在产品性质，不在技术。**

**4.5 我最大的风险判断：会用可见失败被否决。**
泄漏到屏幕（可见）比原文出网（不可见）发现率高一两个数量级。团队会被前者推着走，
去优化「占位符好不好看」，而不是「漏没漏」。`tolerant_placeholder_hits` 必须被立为一号指标并进看板，
**否则这个项目会以一种看起来很成功的方式失败。**

**4.6 我不知道、也无法在本次会话内查证的：**
- 目标环境（政务终端）**是否允许安装本地根 CA**——这是路线 B 的生死判据，且只有人能回答；
- 目标商业 agent（Claude Code / Cursor / Codex CLI 各自版本）**是否做证书固定、是否走 HTTP/3、是否用 IP 直连**；
- **「JEV」到底指什么**——若是某个具体产品，它的延迟/体积/部署形态直接决定 §2.1 层 2 的可行域；
- 小模型在**目标客户机**（不是 windev-01）上的真实前向时延——我只测了本机 64 核 CPU EP 的环境属性，没测过任何模型；
- 真实分布的 PII 语料——`data/cases/rule_cases.jsonl` 那 372 条**是合成的**，
  基线 §六#8 自己说了不能外推。我**没有**任何真实分布数据，任何基于它的精度承诺都是空的。

**4.7 顺便一个不请自来的观察**：基线 §七.1 说工作区有 36 个未提交文件、覆盖全部 S2 安全关键面。
我在这次思考里读的那些文件（`masking/mapper.py` 等）**全都在这个未冻结集合里**——
也就是说上面所有行号引用都可能随开发漂移。我在 `mapping.py` 上看到的容错代码，尤其是
「模型把前缀挪进括号」那几条，很可能就是最近那次 U8 修复的产物。**任何基于行号的结论，复用前请重核。**
