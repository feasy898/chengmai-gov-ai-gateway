## 1. 我怎么理解这个问题：差在哪一环

### 1.1 第一反应（错的）

我最初以为差别是"要不要 MITM"。读基线 §一 + `gateway/app.py:385`（`session_id = request.headers.get("x-anongw-session-id") or deps.new_session_id()`）之后发现不是。

**基线的形态是"客户端知道网关存在"**：用户改 `base_url`、带 `Authorization`、传 `x-anongw-session-id`。这三件事都是**用户知情且配合**的。所以基线的三路由（INTERNET/GOVCLOUD/BLOCK）、会话属主绑定（`gateway/pipeline.py:315` `_bind_session`）、审计归部门，本质上都是**在一个已经被驯化的客户端后面**做安全。

用户要的形态是"客户端什么都不知道"：商业 agent 自带 endpoint、自带 API key、自己决定开不开流、自己重发整个历史。差别不是网络层，是**契约层的四个洞**：

1. **没有会话**。基线的占位符是 HMAC(key, session_id‖type‖normalized)（`masking/mapper.py:222-224`）——session_id 是身份的一半。透明代理拿不到 session_id，就必须自己造，而造错了就完蛋（§3.2）。
2. **没有部门**。基线的 `/internal/restore` 靠部门 key + 属主绑定做鉴权（基线 §六#1）。透明代理里"用户是谁"只有 TLS 会话这一个弱信号。
3. **没有 OpenAI 形状的请求/响应**。商业 agent 的请求体可能是 Anthropic messages、Gemini contents、Responses API。我实测 `GatewayService._restore_choices` 对这三种形状**一个字符都不动**（`gateway/pipeline.py:828-853` 只认 `choices[*].message.content`）。占位符会**原样出网再原样回客户端**——不是泄漏原值（安全上不算破防），但**功能上彻底不可用**。
4. **没有 403 的语义**。基线 BLOCK 是 403 + 文案（基线 §2.3）。商业 agent 收到 403 会重试/换模型/报错给用户。"无感"和"拦截"在透明形态下**直接冲突**。

### 1.2 一句话定性

> **基线缺的不是能力，是"入口"。** 识别→可逆脱敏→流式还原这套内核（`recognizers/` + `masking/`）在形态上是**协议无关**的——`SessionMapper.mask/restore` 只吃字符串，不吃 JSON。真正被绑死 OpenAI 形态的只有三处薄壳：`gateway/pipeline.py`（请求遍历）、`gateway/sse.py`（SSE 组帧）、`GatewayService._restore_choices`（响应还原）。我上面实测的第 3 条洞就是这三处。

这意味着 S3（基线 §七#4 列为"透明代理"未开始）**不是重写，是换壳 + 补三个洞**。这是我全部推论的起点。

## 2. 判定层：规则 / 小模型 / 混合

### 2.1 先纠正一个我以为的结论

我本来以为"要上模型"。跑完 `rule_cases.jsonl` 的统计我改口了：

- **1792 个 expected 实体里 714 个（39.8%）规则层看不见**，PERSON 488 / ADDRESS 172 / WORK_SECRET 42 / DATE_BIRTH 12。这是实打实的洞——**近四成敏感实体在无 NER 的情况下是裸奔的**（基线 §五#1 已登记 NER adapter 恒返回 `[]`，我用数据量化了它的严重性）。
- 但同时：规则层在它看得见的 1078 个上是 **618/618 micro 召回 1.0000**（基线 §表 B），误报 0/45。**这不是"精度不够需要模型补"，这是"召回有结构性缺口"。**

所以我的判断：**规则层不该被替换，该被"绕过"——只在规则层看不见的地方才调模型。** 混合是唯一合理解，而且混合的触发条件应该是"规则层不确定"，不是"每次都问模型"。

### 2.2 混合的形状（我的设计）

```
规则层（~1.3-1.9 µs/字，实测）  →  高置信命中：直接 MASK/BLOCK
        ↓ 未命中且文本像自然语言（非模板/非代码）
小模型（只判"这段里有没有 PII"）  →  有：输出 span + 类型；无：放行
```

关键点：**小模型只做 NER，不做判决**。判决（脱敏还是拦）仍由规则和路由矩阵做（`routing/engine.py:74` `decide` 是纯函数，基线 §2.3 说它 43/43 实测）。这样模型的错误只是"漏一个实体"，不会变成"误拦一句公文"——后者是致命的，商业 agent 里一次误拦就等于产品坏了。

### 2.3 三种方案的权衡（我为什么选混合）

| | 误报 | 漏报 | 时延 | 可解释性 | 我的评价 |
|---|---|---|---|---|---|
| 纯规则 | 低（实测 0/45） | **高（39.8% 实体看不见）** | **~1.3-1.9 µs/字** | 完美（正则可举证） | 兜底层，不可能是全部 |
| 快速小模型 | 中高（开放域误报是它的固有病） | 中 | 我**没测过**，不敢给数 | 差（但可加"高亮证据 span"救回来） | 补 NER 洞 |
| 混合 | 低 | 中低 | 规则段 + 模型段串联 | 规则段完美、模型段可标注 | **选它** |

**我没测小模型的时延，这是个诚实的空白。** 我确认了 venv 里有 `onnxruntime 1.30.0` / `transformers 4.57.4` / `numpy 2.5.3`，但**没有 `.onnx` 权重文件**（`find` 零命中）。`gpu/` 只有部署脚本（基线 §四最后两行：脚本本机未执行）。所以"极快的决策小模型"在这台机器上目前**是纸面的**。

我要说的一个具体判断：**小模型应该只跑在规则层没命中的文本上，且应该跑在 GPU 机（`anolis-gpu-01`，V100S）上经隧道调，不该在 windev-01 上跑**。理由：本机是 Windows Server 无 GPU（基线 AGENTS.md 第一节"无 VT-x"、`gpu/` 目录"本机无 GPU 未验证"），CPU 推理会直接把 §2.5 的时延预算吃掉。但走隧道就多一跳 RTT——**这是我目前最没底的一个数**。

### 2.4 一个反直觉的场景判断

**当用户用的是商业 agent（Claude Code / Cursor / 商业 IDE 插件）时，判定层应该"放宽"而不是"收紧"。** 理由：这些客户端没有 403 的容错语义（§1.1 第 4 点），一次误拦的代价是整个 agent 会话报废，远大于漏一个身份证号。所以：
- 误报 → 灾难性（agent 死了）
- 漏报 → 可接受（用户还是在自己机器上用，只是模型那边看到了）

**结论：商业 agent 形态下，判定阈值应该偏保守（宁可漏、不可误拦），和政务 API 网关形态下的取向相反。** 这两个形态不该共用一套阈值。这是我在读基线时没想到、跑完实验后才明确的一个分叉。

## 3. 部署形态：这是全题最难的一环

### 3.1 五种形态的诚实评估

| 形态 | 安装成本 | 对商业 agent 的适用性 | 我的判断 |
|---|---|---|---|
| **网关 API**（基线现状） | 零（改 base_url） | **差**——商业 agent 的 endpoint/TLS 不归你管 | 内网政务场景已经够了，不要动 |
| **SDK 封装** | 改调用代码 | **差**——等于要求用户改 agent | 只适合自己写的应用 |
| **HTTP_PROXY 环境变量** | 极低 | **中**——Node/Python 系的 agent 常认 `HTTPS_PROXY` | **性价比最高的"无感"起点** |
| **本机透明代理（mitmproxy + CA）** | 中（装 CA、装 mitm、装 add-on） | **不确定，是最大风险** | 见 §3.2 |
| **IDE / 浏览器插件** | 中高（要匹配 IDE 扩展 API） | **好**——插件在 agent 的进程内，能直接读改 prompt | 见 §3.4 |

### 3.2 透明代理这一环，我认为它被高估了

三个具体的硬伤，按严重度排：

**（a）TLS 证书固定。** 商业 agent 如果做 pinning，自建 CA 直接死。我不知道主流商业 agent（Claude Code / Cursor / Cline）当前是否 pinning——**这是我不知道的第一件事**，只能实测。
**（b）非 OpenAI 协议。** 我实测了 `gateway/sse.py:61` `iter_sse_data_lines` 是**按 `data:` 行解析 SSE** 的。Anthropic 的 event-stream、Gemini 的流格式都不同。基线的整条 SSE 管线在非 OpenAI 协议上**不能直接用**。
**（c）HTTP/2 与连接复用。** 商业 agent 普遍用 HTTP/2 + keep-alive，mitmproxy 的支持面我记得是有的但没验证。

**但我要给透明代理一个公道**：它有一个别的形态没有的性质——**它能看见用户根本不知道自己在传什么**。如果用户的诉求其实是"合规审计"（谁在什么时候把什么发给了哪家商业模型），透明代理是唯一答案。如果是"防泄漏"，那 §3.3 的占位符方案就够了，透明代理是杀鸡用牛刀。**这两个诉求会导出完全不同的产品。**

### 3.3 我做的最有价值的一个实验：占位符形态存活率

这是我认为本题真正的技术核心，所以我自己跑了。模拟商业 agent：**用一个我控制不了的系统提示词**（"你是一个乐于助人的通用 AI 助手…尽量使用表格和列表"），三种占位符形态 × 6 类改写任务 × 3 次重复：

```
A 全角（基线现状）〔人名·4e3e3778〕        → 16/18
B ASCII 标签+ID  <PERSON_4e3e3778>          → 17/18
C 裸编号         #4e3e3778                  → 15/18
```

**三个结论，每一个都推翻了我的一个预设：**

**结论一：占位符形态几乎不影响存活率。** A/B/C 差距在噪声内。我原本以为 ASCII 更抗改写（因为模型不会把 `<PERSON_x>` 当中文标点处理），实测没有。**"选一个更好的占位符形态"这条路是伪路——不值得投入。**

**结论二：注入系统提示词规则，价值巨大。** 同样 `table` 任务，注入规则 **6/6**，不注入 **5/6**（丢的那次是 `steps` 任务，模型把 3 个标识符全丢了，只在末尾解释里提了两个）。更早一轮 `json` 任务不注入时模型甚至把 label 和 digest **拆到两个字段**。**这解释了为什么基线的 T8.4 要做那么复杂的"容错改形还原"——因为模型本来就会拆它。** 我一开始以为容错还原是锦上添花，实测发现它是**主路径上的必需品**。

**结论三（最重要的）：有一类失败是正则原理上救不回来的。** 模型输出表格时把 label 和 digest **拆到不同单元格**：

```
| 申请人（人名） | （原文未显示具体姓名） | 4e3e3778 |
```

label-digest 的**绑定关系被表格结构本身破坏了**。我实测 `restore_tolerant` 对这种输出原样放行。而 `canonical_placeholder`（`masking/mapper.py:110-135`）要求"括号内恰好两段、中间恰好一个间隔号变体"——拆开就不符合形状。

**我一开始的错误认知**：以为只要还原正则写得够宽就能全覆盖。实测打脸：**当模型重组结构时，信息在语义层丢了，正则层无解。** 基线的 11 种改形目录（`docs/assets/specs/masking-placeholder.md:131-137`）覆盖的是**字符级改写**，不覆盖**结构级重组**。这是基线资产的一个真实缺口，我认为是 S3 必须先补的。

### 3.4 我真正看好的路线：`HTTP_PROXY` 显式代理 + 强可解释回退

理由：
- 装一个环境变量 = 真正的"无感"，不改 agent 代码、不装 CA、不装插件；
- Node/Python 系的商业 agent 和 SDK 大多认 `HTTPS_PROXY`（**我没实测这一点**）；
- 失败时是**响亮失败**（连接拒绝）而不是**静默降级**，符合"用户无感但系统不骗人"。

我给它的定位是：**不是最优雅，但是最快能拿到真信号的形态**。真正的产品形态可能要往上走一层（插件 > 代理），但代理形态能让我在**不碰 CA、不碰证书固定**的前提下，先把 §3.3 的还原问题在真实协议上跑透。

### 3.5 我给基线的一个具体改进建议（如果人类要拍板）

`tolerant_placeholder_hits` 是 U8"零泄漏"断言的唯一检测面（`ops/e2e_smoke.py:1273`）。我实测：喂给它一个**括号被剥掉**的占位符 `手机号·e3104883`，它返回 `[]`。

也就是说：**一个功能上已经坏掉的输出（用户看到 `手机号·e3104883` 这种鬼东西），U8 断言判 PASS。**

修复很小：给检测面加一个"裸 `标签·hex8-12`"的第二正则（不需要括号作为锚，因为查表命中仍是终审闸——和 `mapper.py:161` 现有的防误替机制同构）。这是我这次唯一一个"我认为基线有真实缺陷"的发现，且**我有实测证据**。

## 4. 回写层：会话一致性——这是我认为最大的隐形坑

### 4.1 基线的机制

`session_id` 参与 HMAC（`mapper.py:222-224`），所以：同 session 同值恒同占位符，跨 session 必不同。我实测了多轮：
```
T1: 我是〔人名·4752d4d3〕，手机〔手机号·6f1c6722〕
T2: 再问一下，还是〔人名·4752d4d3〕，另外〔人名·4288e00a〕的身份证是〔身份证·5224c3e6〕
```
同 session 内"张三"两次都是 `4752d4d3`。**跨请求一致性在"session_id 稳定"的前提下是白送的。**

### 4.2 但透明形态拿不到 session_id

我先想了一个显然的方案：**用连接当会话**。立刻否掉——商业 agent 全部走 HTTP keep-alive，一个连接上跑几十轮不同话题，连接级会话会让占位符跨话题污染。

第二个方案：**用对话前缀哈希当会话**。问题是这需要一个"对话已经开始"的锚点，而请求是逐条到达的。

第三个方案（我现在倾向的）：**两段式**。
- 第一轮：代理**同时**用两种占位符发出去（`〔人名·4e3e3778〕` 和 `4e3e3778`），或者发一个带"若上述符号是占位符请原样保留"的 system prompt；
- 第一轮回包时，代理**按实际出现的形态**锁定 session 内的形态（存进 `session_map` 的一个偏好位）；
- 后续轮次按锁定形态发。

这个设计我**没有实现也没有验证**。我意识到它有个致命前提：**商业 agent 允许我注入 system prompt**——而 §3.1 的表里，"允许注入 system prompt"恰恰是插件形态才有的能力，代理形态**不一定有**（取决于客户端是否允许覆盖 system 字段）。

**所以 §3.4 的 HTTP_PROXY 路线有一个我至今未解的问题：拿不到 system 注入权，就拿不到 §3.3 结论二的那 6/6。** 这是我路线里最脆弱的一环，明说。

### 4.3 流式 chunk 切占位符

这一环我确认**基线已经做对了，不需要重做**。`StreamRestorer`（`masking/remap.py:50-120`）只有一个 `_pending` 状态、缓冲 ≤48 字符（`MAX_PLACEHOLDER_LEN`）。我实测所有切点（1 到 len+1，每个切点）都正确还原。基线 §表 B 的"500 组/例 fuzz == 整段（byte-exact）"我**没有重跑**，这是转述。

我自己的判断：**流式切块对"无感工具"形态是必备的，而且它是基线最被低估的资产**——因为商业 agent 几乎全部默认开流式。基线在这块的成熟度（t0_stream 14/14）远高于它的宣传口径。

**但流式有个代理形态特有的新问题**：代理要边收边改，SSE 的 `data:` 行边界在 HTTP/2 和代理层可能被重排。`iter_sse_data_lines` 假设的是字节流顺序（`gateway/sse.py:61`），这个假设在字节级代理下是成立的，但如果客户端有请求并发/多路复用，需要按 SSE 的 `id:` 字段做分流。**我怀疑这里会出问题但没验证。**

## 5. 性能预算：用户无感意味着多少

我实测的数：
- 检测层：**1.3–1.9 µs/字线性**（2000 字 = 2.57ms 中位）
- 多轮累积：10 轮 2120 字 = 2.85ms 中位，**线性增长不爆炸**
- 脱敏（2000 字 / 39 占位符）：0.06ms
- 还原（同上）：0.21ms

**我的时延预算判断**（这是我的主张，不是基线数字）：

| 环节 | 预算 | 理由 |
|---|---|---|
| 检测 + 脱敏 | **< 30ms** | 用户对首字延迟的感知阈约 100ms；30ms 是安全的 3 倍余量 |
| 还原（流式，按整条响应） | **< 10ms** | 流式是逐块，还原本身是 O(n) 单遍 |
| **小模型段（如果走隧道）** | **< 200ms** | ⚠️ **这一行我完全没测** |
| 代理网络开销 | < 5ms | 同机回环 |

**如果小模型段真要走隧道且是 200ms，那"用户无感"就破了。** 这是我的方案里最大的未验证假设。有两条退路：
1. 小模型跑本机 CPU（牺牲吞吐换 RTT）——但本机无 GPU；
2. 小模型跑本机但只在**首次**对一个会话跑一次，结果缓存——但漏报面扩大。

**我倾向于：先用纯规则跑通形态，把小模型当 v2。** 因为规则层 39.8% 的缺口是**召回问题**，而召回缺口在这个产品形态下的后果是"某个身份证号没脱敏"，不是"产品不能用"。**先把形态跑通、再补召回**——这是我的信心排序。

## 6. 我认为最可能成功的路线

### 路线 A：SDK/网关 API 形态的延伸（信心 0.85，但**不解决用户的问题**）

把基线的三个薄壳（pipeline/sse/_restore_choices）抽象成协议无关的 `mask_stream(text) -> text`，然后补 Anthropic / Gemini / Responses 三种响应形状的还原。

我实测这一步是**真的缺**（三种形状一个字符不动）。做完之后基线就能服务非 OpenAI 上游。但**用户是商业 agent，这个路线对他们无效**。所以我给它的信心高、但承认它不对题。

### 路线 B：`HTTPS_PROXY` 显式代理 + 协议无关还原（信心 0.55）← **我押这条**

理由：
- 真"无感"（一个环境变量）；
- 不碰 CA、不碰证书固定、不碰 pinning；
- 失败响亮（连不上，而不是静默漏）；
- 能复用基线 90% 的资产。

**信心只有 0.55，因为两件事没验证**：(1) 商业 agent 是否认 `HTTPS_PROXY`；(2) 没有 system 注入权时占位符形态是否稳定（§3.3 结论二显示注入价值很大）。

### 路线 C：IDE/浏览器插件（信心 0.40，但对"商业 agent"最对口）

插件在 agent 进程内，天然有 system prompt 注入权、拿得到会话、能处理非 OpenAI 协议。**技术难度反而最低。** 但我给低信心是因为：插件要一个个适配（IDE 扩展 API 各家不同）、分发和信任问题、用户在企业环境装插件要过审批。**这是产品问题不是技术问题，而我判断产品问题的确定性低于技术问题。**

### 我会先做的实验（按顺序，专为证伪路线 B）

1. **验 `HTTPS_PROXY` 是否被主流商业 agent 认**（哪怕用一个自建 echo 服务 + 一个最小 Node 客户端）。**成本 10 分钟，直接决定 B 生死。**
2. **验证书固定**：真实商业 agent 直连时是否接受自建 CA。**成本取决于 B 的结果。**
3. **无 system 注入权时的占位符存活率**（我要在真实商业 agent 上重跑 §3.3 的 A/B/C 实验，拿到真实的、不是我造的提示词下的数字）。
4. **协议面**：把真实流量抓下来，看它到底是不是 `data:` 行的 SSE、body 是不是 OpenAI 形状。

**第 1 和第 3 条是 go/no-go。第 4 条决定要不要重写 `gateway/sse.py`。**

## 7. 最大的风险 / 我不知道的事 / 需要人类拍板的分叉

### 7.1 风险（按我的判断排序）

1. **占位符被模型结构化重组后不可还原**（§3.3 结论三）。这是**原理性**的，不是工程 bug。基线的 T8.4 容错面不覆盖它。
2. **会话一致性在透明形态下无解**（§4.2）。如果拿到不稳定的 session_id，占位符会跨轮跳变，用户看到"同一个张三前后两个名字"。
3. **小模型时延未测**（§5）。可能直接破掉"无感"。
4. **"无感"与"拦截"语义冲突**（§1.1 第 4 点 + §2.4）。拦截就不无感，无感就不能拦。**这个矛盾我认为没有纯技术解法，需要产品层面接受"透明形态下只脱敏不拦截"。**
5. **基线工作区未冻结**（基线 §七#1，36 个文件未提交）。任何形态改造前应该先冻结——否则我今天读到的代码明天可能没了。

### 7.2 我明确不知道的

- 主流商业 agent（Claude Code / Cursor / Cline）当前**是否做 TLS pinning**——未实测；
- 它们**是否认 `HTTPS_PROXY`**——未实测；
- 它们**是否允许覆盖 system prompt**——未实测；
- 小模型 NER 的**真实时延**——本机无权重，未测；
- 我的存活率实验用的是 **local-chat-8b**（本机 8B），**不是商业模型**。商业模型（Claude/GPT）能力更强，**存活率只会更高不会更低，但这是我推测不是实测**。

### 7.3 需要人类拍板的分叉（我真的不知道答案）

**分叉 1：这是一个"合规工具"还是"防泄漏工具"？**
- 合规 → 需要看见全部出网流量 → 透明代理是唯一解 → 接受 CA 安装成本和失败模式
- 防泄漏 → 占位符方案足够 → 不需要碰 TLS → 路线 B/C
**这两个的架构完全不同。我目前的全部推论建立在"防泄漏"上，如果真实诉求是"合规"，路线 A 才是起点。**

**分叉 2：透明形态下允许"拦截"吗？**
不允许 → 阈值偏保守（§2.4），宁可漏不可误拦
允许 → 需要一个用户能理解的中断机制，而商业 agent 大概率没有这个机制
**我倾向不允许，但这是产品决策不是技术决策。**

**分叉 3：审计目标是什么？**
审计"用户说了什么"（提示词侧）→ 需要看见全部出网流量 → 透明代理
审计"网关转发了什么"（代理侧）→ 基线现有审计够用
**基线的审计是严格的零明文（基线 §2.5，65536B 扫描 0/7 命中）。如果新形态要记"用户原始输入"，这条红线就得重开一个口子——这是我不愿意做的，但我知道如果分叉 1 选"合规"就绕不开。**

## 8. 收束：我这次真正改变了什么想法

写下来留档，三条自我修正：

1. **我原以为"占位符形态设计"是本题核心技术核心**。实测三种形态 15-17/18，差距在噪声内。**这条路是伪路。** 真正的核心是**模型会不会重组结构**（label-digest 绑定被破坏），而这是正则原理上救不回来的。
2. **我原以为透明代理是"下一步"**。现在我认为它是**最难的一步，且可能不该第一步做**。它要解决 CA、pinning、非 OpenAI 协议三件事，而这三件都不是基线的强项。更快拿到真信号的是 `HTTPS_PROXY`。
3. **我原以为"补 NER 模型"是刚需**。数据说 39.8% 实体规则层看不见（严重），但时延预算说小模型可能吃掉整个无感预算（致命）。**先用规则跑通形态、再补召回**——这是我最后的判断，也是我信心最高的一句。

**基线最被低估的资产，我认为是流式还原**（`masking/remap.py`）。商业 agent 几乎全部默认开流式，而基线在这块是 14/14 实测全绿、缓冲有界、fuzz byte-exact。**它不需要被改造，它需要被复用。**
