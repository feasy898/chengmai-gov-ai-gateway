## 一、我如何理解这个问题：差距不是一个环节，是三个

基线一句话（§一）：OpenAI 兼容网关，客户端照常调 `/v1/chat/completions`，网关完成识别→可逆脱敏→敏感度路由→转发→还原→输出防护→审计。16/16 模块三族实测全过（§三表A）。

我最初把问题概括成"基线是 API，用户要的是产品"。推下去发现这个概括太粗，会误导方案选择。真正被"无感"二字击碎的，是基线形态依赖的**四个客户端配合条件**：

1. **Endpoint 可配**——客户端必须肯把请求指到网关；
2. **部门 key**——鉴权靠客户端出示 key（§2.8：无 key/错 key 401，跨部门复用会话 403 属主绑定）；
3. **会话 ID**——占位符一致性与还原都挂在客户端传的 SESSION_ID 上（§2.8 形态闸）；
4. **OpenAI 协议**——解析面是 OpenAI chat 协议（§2.8 出站检测面也是围绕它的 dict/tools/多模态段）。

商业 agent（自带 endpoint、自带 TLS、可能证书固定、协议各家不一）天然不满足这四条。所以差距可以拆成**三个独立问题**，我一开始只看到第一个：

- **A. 捕获问题**：流量怎么到我手里（部署形态，本次切入角）；
- **B. 身份与会话问题**：没有 key、没有 SESSION_ID，占位符一致性和"谁能还原"靠什么成立；
- **C. 协议覆盖问题**：OpenAI 协议之外，Anthropic 协议、各家私有协议、甚至网页版聊天（根本不是 API）怎么解析出文本字段。

这三个问题几乎正交：捕获形态选得再好，B/C 不解照样白搭。基线 §七#4 的路线图里 S3（透明代理）未开始——这个 ask 本质就是给 S3 做方案思考，但 S3 一词只覆盖了问题 A，我提醒自己别让路线图的措辞把 B、C 缩没。

## 二、部署形态空间：逐个过堂（切入角）

### 2.1 网关 API 模式（基线形态）

安装成本：每个 app 一次配置。适用面：**endpoint 可配置的一切客户端**。致命障碍：无——客户端把网关当源站，TLS 在网关终结、网关自己向上游建连，**证书固定在此形态完全无关**。这是它压倒一切 MITM 形态的工程优势。

关键实证来自本机 AGENTS.md：zcode 的配置就是 `provider...baseURL` 字段（AGENTS.md §七），kimi 是 `config.toml` 里的 `base_url`（§八）。也就是说，**"CLI 编码 agent"这一大类商业 agent 今天就能用纯配置接入基线**，一行代码不用写。我一开始默认"商业 agent = 封闭不可配"，这个默认是错的：商业 agent 有谱系，从"全可配的 CLI"到"硬编码 endpoint 的桌面 app"是一条连续谱，方案应该按谱系分层，而不是选一种形态打天下。

### 2.2 本地显式代理（HTTP_PROXY/HTTPS_PROXY）

我先有个想当然：显式代理可以只做 CONNECT 隧道、不碰内容，安装成本低。**后来意识到这是错的**：不终结 TLS 就看不到明文，脱敏无从谈起——所以显式代理只要想做内容级脱敏，就必然 MITM + 自建 CA，在"内容可见性"上与透明代理等价。两者的真实差别只剩一个：**流量怎么被引到代理**（环境变量 vs 流量重定向）。

显式代理的具体成本清单：

- CA 分发是**按运行时逐个打**的，不是装一次系统就完事：Windows 系统证书店覆盖 Chromium/Electron/.NET；Python `requests` 默认用 certifi 自带包（要 `REQUESTS_CA_BUNDLE`/`SSL_CERT_FILE`）；Node 要 `NODE_EXTRA_CA_CERTS`；Firefox 用 NSS 独立店。漏一处，那个 app 就握手失败——这既是安装成本也是**暴露的失败信号**（好事，见 §7 fail-visible）。
- 服从性不保证：Python/Go 标准栈普遍认 env 代理；不少 Electron 桌面 app 不认。不认的 app **静默直连**，工具毫无感知地失效——这是我最反对的 fail-open 面。
- 对"按快捷方式启动"的桌面 agent，可以做**wrapper 启动器**（一个 .cmd/快捷方式：设 env + CA 环境变量 + 拉起 app），把"全局安装"降为"每 app 一个入口"，成本很低、覆盖明确、可审计。这在 Windows 政务办公机上是很自然的发放形态。

### 2.3 本机透明代理（TUN/SNI 分流）

覆盖最强（对 app 零要求），工程上最脆：

- Windows 上没有原生 mitmproxy 透明模式，实际路径是 TUN（wintun + sing-box/mihomo 类）把 SNI 命中的域引到本地 MITM 口。本机（windev-01）**已跑 tailscale**，两个 TUN 栈共存的路由表交互是真实坑位，先要在可丢弃环境验证。
- **HTTP/3/QUIC**：若 agent 走 UDP 443，TCP 系 MITM 直接看不见；需对这些域封 UDP 443 逼降级 TCP（业界常规做法）。
- **证书固定**：我一开始把 pinning 当作一票否决的致命障碍，后来修正：pinning 只威胁 MITM 形态，且它决定的是"**哪个 app 归哪条路线**"，不是"路线是否成立"。CLI 类 agent 几乎都走标准 TLS 栈不 pin；封闭桌面 app 才有风险。正确姿势是**pinning = 排除名单**（该 app 回退到 2.1/2.2 或明确告知不覆盖），绝不做绕过。
- SNI 白名单把爆炸半径限制在 LLM 域名集合，这个必须坚持：全域 MITM 在政务机上既不必要也不可接受。

### 2.4 浏览器/IDE 插件

浏览器插件只覆盖网页版聊天：载荷是各家私有 JSON/websocket 形态且随版本漂移，Manipulation-in-content-script 脆弱。IDE 插件基本退化为"帮你改 proxy 设置"，即 2.2。判断：**不是第一批**，除非政务用户主力是网页聊天——这本身是我不知道的事（§7）。

### 2.5 SDK 封装

只适用自家应用，对现成商业 agent 无效。作为基线既有能力的延续保留即可。

### 小结

覆盖—成本曲线：endpoint 配置（2.1）< wrapper+env 代理（2.2）< TUN 透明（2.3）< 插件（2.4）。我的排序是 **2.1 → 2.2 → 2.3 递进**，2.4 缓。并且 2.2/2.3 有一个共同的非拦截执行面：**防火墙/进程级规则把 LLM 域名的出网限制为只允许代理进程**——即使某 app 不服从 env 代理也无法静默直连。这把"防绕过"从工具内移到边界，是 fail-closed 的正确位置。

## 三、判定层：规则、小模型、还是混合

先把基线的实测面摆正（§2.1、表B）：结构化号码 micro 召回 1.0000（618/618，校验位背书）、2000 字检测 ≈2ms、白名单误报 0/22。**在身份证/手机号/统一社会信用代码这类结构化实体上，规则+校验位已经到顶，任何模型的边际增量为零，反而引入不可解释性和新的 FP 面。**

真正的洞在开放词汇：NER 恒空、人名只有 4 个演示名 + 姓氏启发式 0.5 置信、住址规则层零产出（§5#1、§6#9，feedback.md 自认"演示人名现场穿帮"）。规则层词表外漏检是**固有**边界。用户提的"JEV 式极快决策小模型"，增量恰好也只有这里。

我的立场（推完后我坚持的一个明确分界）：**模型当识别器，不当处置器**。即：小型 NER（人名/住址/机构名 token 分类）把候选实体喂进既有 masking 管线，供 rule+policy 做定性；而"拦截/政务云/放行"的路由决策保持规则与策略可解释——政务场景里处置必须可审计、可申诉，黑盒路由过不了合规这一关。判定层的级联 thus：确定性规则先行（成本≈0、精度极高）→ NER 只补人名/住址类 → 都不确定的按保守策略（脱敏或提示）。时延估算（标注：估算，未实测）：蒸馏级 NER 在 CPU 上 2000 字约 5–30ms，V100 上 1–3ms + tailnet RTT 5–30ms——都藏得进下面的预算。

无感形态放大了一个被低估的代价：**FP 是静默的质量劣化**。误脱敏一个产品名/项目名，LLM 答非所问，用户不知道为什么变笨了。所以判定层阈值要按"无感"口径重新调，宁可给用户一个轻量的"本条已脱敏 N 处"提示（见 §7 拍板项）。

## 四、回写层：占位符设计、无会话一致性、流式

### 4.1 占位符与 LLM 的对抗性

占位符要同时满足：LLM 愿意原样复读、还原方正则稳健、不像敏感数据、不破坏 markdown/JSON。基线已验的是**形态层容忍**：残缺/改形占位符逐字节还原、负例原样放行（§2.2，t0_stream 14/14）。未验的是**语义层变异**：LLM 把占位符换成代词、干脆丢掉、"帮忙"改写成别的记号。方向上这是 fail-safe 的——还原失败的用户看到的是残留占位符或信息缺失，而**不会还原错人**：restore 依赖映射表命中终审（§6#11），编造的占位符命中不了真实映射。信息损失可接受，张冠李戴不可接受，失败方向是对的。

### 4.2 系统提示词注入占位符契约可靠吗

在网关/MITM 形态下，工具技术上**可以**给请求注入一条系统消息（"形如 [X_yyyy] 的是用户真实数据，回复时原样保留"）。但对商业 agent 的模型这条契约是概率性服从的——尤其在翻译、总结、JSON 输出等指令冲突场景。基线 U8 真实腿"回复占位符零泄漏"（§2.8）只证明了自家链路，不外推到任意商业 agent。这必须实验测定（§六实验2），不能拍脑袋。

### 4.3 无会话 ID 的一致性——这里基线白送一块

我原以为 B（身份/会话）是无感形态最难的点，细看后修正：基线占位符是**内容摘要寻址、同会话恒同、10 万次插入零碰撞、同摘要自动升位**（§2.2）。也就是说一致性来自映射表本身，SESSION_ID 更多承担属主隔离（§2.8）。无感形态下：映射表 = 会话。用 (进程，目的域) 桶 + TTL + LRU 近似会话即可获得跨请求占位符一致；代价是要重选盐策略——基线"跨会话互异"是防跨部门链接的隐私特性（§2.2），单用户本地形态下按天/按进程加盐即可，链接面本来就小。残余问题：同用户两个并行会话提到同一个"王五"会共享占位符（功能性无损，链接性略有），以及多轮指代（"把他的电话发我"）依赖模型自己用上文占位符作答——这恰是 4.2 要测的。

### 4.4 流式

已被基线解决到可复用：500 组/例切块 fuzz 与整段 byte-exact、缓冲 ≤48 字符（§2.2）。无感形态的增量工作在传输层不在语义层：MITM 需要 gzip/br 解压重写、SSE 帧、h2；这些是工程量不是风险。

顺带一个收缩攻击面的观察：无感形态下还原发生在本地工具进程内，不再需要基线 `/internal/*` 那张含还原原文的网络面（§6#1）——本地化的还原 API 面**小于**基线。但 `session_map.db` 明文落盘（§6#6）在本地同样成立，DPAPI 加密是便宜的正解。

## 五、性能预算："无感"的数字

锚点全部来自基线实测（表B，单机单次口径）：识别 ≈2ms/2000 字、还原 ≈0.26ms/50 占位符。无感预算我的推导：聊天场景 TTFT 普遍 300ms–2s，**发送前附加处理 ≤50ms（p95）在体感上不可见**；规则-only 路径 p50 在 10ms 内毫无压力，加 NER 也在预算内（§三估算）。真正会"被感觉到"的是：模型冷启动（秒级）——NER 必须常驻；以及流式还原的缓冲——≤48 字符缓冲在慢速 token 流下最坏拖个尾，需保留基线的"命中即冲刷"语义。本地代理自身的转发开销（mitmproxy 量级 1–5ms/hop，估算）可忽略。结论：**性能不是这个产品的约束，正确性才是**；预算给判定层留了充足余量，反而要防的是"反正很快，什么都过一遍模型"的过度设计。

## 六、最可能成功的路线与证伪实验

**路线 A（信心 0.85）：回环网关 + 配置/env 双轨覆盖。** 基线原样前置到 127.0.0.1，HTTP 明文听回环（无 TLS 问题、无 pinning 问题）；CLI/可配 agent 走 baseURL 配置（zcode/kimi 已实证可配，AGENTS.md §七/§八），不配合的 app 走 wrapper 启动器 + env 代理 + 按运行时 CA；边界配防火墙规则只许代理进程出网 LLM 域名。多协议适配器先 OpenAI、再 Anthropic。这是纯增量工程，安全能力全部复用已验收管线。

**路线 B（信心 0.6）：A + TUN/SNI 白名单 MITM 兜底。** 只为硬编码 endpoint 且不 pin 的封闭 app 服务；pinning 命中即转排除名单。 tailscale 共存与 QUIC 是先决验证项。

**路线 C（信心 0.35，缓行）：浏览器插件**，待确认政务用户是否主力用网页聊天。

**证伪实验（按杀伤力排序，都是半天到一天量级）：**

1. **Pinning 探测**：对本机在用的 kimi.exe/zcode + 任一封闭 agent，挂裸 mitmproxy + 装 CA，看握手成败。若 CLI 类全过、封闭类部分 pin，则 A/B 分层成立；若连 CLI 都 pin（意外），A 仍成立（不依赖 MITM），B 收缩。
2. **回显保真率**：经 ：9004 真实腿跑 100+ 轮：有/无系统提示词注入两种条件下，测占位符在多轮回指、总结、翻译、JSON 输出四种任务下的存活率。**这是整套无感思路的天花板实验**：若无注入条件下存活率 <95%，4.2 的契约不可依赖，产品必须内置注入或接受降级还原。
3. **无会话一致性**：10 轮对话 × 无 SESSION_ID × LRU 映射，测占位符一致率与串话率。
4. **端到端附加时延** p50/p95：rules-only vs +NER（含常驻内存的暖态），对照 50ms 预算。
5. **env 代理服从性普查**：逐个测目标 agent 是否认 HTTPS_PROXY（决定 wrapper 覆盖率与防火墙规则的必要性）。

## 七、最大的风险、我不知道的事、需要人拍板的分叉

**风险**：① LLM 语义级改写占位符（4.1/4.2）——唯一可能动摇方案根基的，实验 2 先行；② 开放词汇 FN 在 MITM 形态下被放大（拦的 app 多了、审计面却没跟上，NER 又是空的，§5#1）；③ 静默绕过/静默失效——所有"看起来在工作"实则直连的路径；④ 门禁环境敏感的既知问题（§7#2/#3、§6#15/16）提示：无感工具作为**常驻进程**对环境的稳定性要求比按批跑的网关高一档。

**我不知道的事**：目标商业 agent 的确切清单与其网页版/桌面版占比；政务办公机是否允许装 CA + TUN 驱动（管理员权限）；目标 app 里谁真的 pin；政府侧能否接受"高危内容在商业 app 里以报错形式显式失败"（基线是 403，无感形态下 403 会以商业 app 自己的报错冒出来，用户必然有感——我认为这**应该**有感，但要人确认）。

**需要人拍板的分叉**：① 目标 app 清单与优先级（决定 A/B/C 资源配比）；② 无感的边界——我主张"体验无感、防护状态不无感"（托盘/轻提示告知已脱敏 N 处、拦截时明示），完全静默会在质量劣化时摧毁信任；③ 盐与会话策略（隐私 vs 便利）；④ MITM 形态下敏感度路由还要不要做（技术上可行：代理终结 TLS 后可自选上游，但商业 agent 的凭据体系与政务云腿不通，协议翻译复杂度陡增）——我倾向于第一期砍掉路由只留"脱敏+还原+拦截+审计"，路由留给自家网关腿。

**开放问题**：占位符格式在不同模型 tokenizer 下的稳定性（会不会被切成怪 token 影响复读）未查证；多模态段（截图里的 PII）在无感形态如何覆盖，基线检测面已扫非文本段（§2.8）但 MITM 形态的图片改写基本不可行——先声明不覆盖。
