## 一、我怎么理解这个问题：差的不是"加个代理"，是"谁提供 session"

人类原话里最容易读成的一句话是"套个透明代理就无感了"。我一开始也是这么想的。读基线的时候我发现 `盘点/基线总文-gov-anon-gateway.md` §七.4 写"后续路线：S3（透明代理）……均未开始"，而工作区里 `.zcode/plans/plan-sess_abea545a-*.md` §3.1 已经把 S3 方案写得很细了（mitmproxy addon + `--allow_hosts` 只对 AI 域名 MITM + Windows 信任库导入脚本 + hosts 演示模式）。**也就是说"补一个透明代理"这件事，前一个会话已经设计完了。** 如果我交给人类的第一句话是"应该做透明代理"，那我是把别人已经做完的调研又端上来一遍，没有任何增量。

那真正没做的是什么？我去读代码，找"显式 API 网关形态"和"无感工具形态"的结构性差异，找到三处：

**差异一：session 是正确性的单位，而无感形态里没有人提供它。**
`gateway/app.py:385-389`：

```python
client_session = request.headers.get("x-anongw-session-id")
if client_session is not None and not SESSION_ID_RE.fullmatch(client_session):
    return _error_response(400, ...)
session_id = client_session or deps.new_session_id()
```

客户端不带这个头，就每次请求现造一个 session。而占位符的 digest 把 session_id 掺进去了（`masking/mapper.py:222-224`，`msg = f"{session_id}\x1f{type}\x1f{normalized}"`）。于是同一个身份证在第 1 轮和第 2 轮会得到两个不同的 token。我实测了（见下），**多轮一致性直接崩**：模型在自己的历史里看到"上一轮我说 〔身份证·5f44afc0〕，这一轮同一个身份证变成了 〔身份证·3b0376b5〕"，它要么困惑要么胡编。所谓"可逆脱敏"在这一刻就不成立了——不是还原失败，是**语义不一致**。

基线为什么没暴露这个问题？因为基线形态里客户端总是显式带这个头（WebUI 带的、标准 OpenAI SDK 客户端可以配的），16/16 验收模块测的也全是"显式传 session"的路径。**这是一个在验收全绿的产品里藏着的、只有"无感"才会踩的坑。** 这才是差的那一环。

**差异二：协议形状。** 基线的检测面其实比我预想的宽。`gateway/pipeline.py:213-241` 的 `_aux_texts` 遍历除 `messages`/`stream` 外的**全部顶层键**，再对每个 dict/list 递归取字符串叶和键（`_iter_string_leaves`，`pipeline.py:161-178`）。我实测确认 `instructions`（新式 OpenAI）和 `system`（Anthropic 是顶层数组不是 message）都在检测面内：

```
aux (top-level non-messages/string leaves):
   'm'
   '你正在为张三（身份证 11010119900307461X）办理低保，联系电话 13800138000'
   '[{"type":"text","text":"内部资料 不得外传 密级★"}]'
detect on aux faces:
   HIT ... [('人名','张三'), ('身份证','11010119900307461X'), ('手机号','13800138000')]
   HIT ... [('密级标识','内部资料'), ('密级标识','不得外传')]
```

这说明**出站检测面比入站消息面更通用**——`_aux_texts` 是结构无关的。重建侧 `_apply_aux_masked`（`pipeline.py:243-255`）按"原串→脱敏串"精确映射回填，也能对上。**但响应侧不是。** `gateway/sse.py` / `pipeline.py` 的还原逻辑是硬编码 OpenAI 形状（`choices[0].delta` / `message.content` / `tool_calls[].function.arguments`）。Anthropic 的 `/v1/messages` 流是 `content_block_delta` / `input_json_delta`，Gemini 是 `candidates[].content.parts[].text`，Responses API 又是 `response.output_text.delta`。**出站可以靠"深度 JSON 扫描"泛化，入站还凑合，响应侧必须逐协议重写。** 而响应侧恰恰是"还原"发生的地方。这是无感形态下最被低估的工程量。

**差异三：映射表的位置变了，而它的内容是明文。** 基线 §六.6 自己写了：`session_map.db` 按设计存归一化原值、未加密，"文件泄露 = 占位符全量反查"。在政务云形态里，这是一个受控内网数据库上的残余风险；在无感工具形态里，这张表**长在用户自己的笔记本上**。同样一个残余风险，产品形态一变，等级就变了。基线 §2.5 那套"库文件 bytes 级扫描 0/7 原值命中"的零明文审计，验的是**审计库**不含明文；`masking_map` 按设计就必须含（spec `masking-placeholder.md` §4 明确两库分文件的原因就是这个）。所以无感形态下"这台机器上有个文件，拿到就能把所有占位符反查回身份证"是**设计使然**，不是 bug。这需要人类拍板，不是我能定的。

**差异四（我一开始完全没想到）："无感"和"拦截"在语义上互斥。** 基线的 BLOCK 是 403 + `CLASSIFICATION_MARK` 理由（§2.3，三族实测不触达上游）。在显式网关形态下，调用方是知道自己接了网关的，403 是一个可编程处理的信号。在无感形态下，商业 agent 收到一个它不认识的 403，agent 的表现是"工具坏了/重试/降级"，用户看到的是"AI 不好用了"。**"命中密级标识就静默阻断"这件事，在无感形态下无法无感。** 要么给用户看提示（那就有感了），要么给 agent 看提示（那 agent 可能自己绕过），要么静默降级（那安全策略失效）。这个三角我解不了，必须是人类拍板。

## 二、方案空间

### 2.1 判定层：我实测之后改变了立场

**我一开始的直觉**：需求里说"类似 JEV 那种速度极快的小模型"，那大概是要上小模型。

**我实测之后的想法**：规则层已经够快，快到上模型的理由不是速度，是召回。

```
detect ms: min=1.433 med=1.507 max=8.666  findings=60     # 1236 字，30 次
mask   ms: min=0.103 med=0.152 max=0.562  masked_len=1368
restore ms: min=0.285 med=0.307 max=0.424  back_to_orig=True

# 拟真 agent 请求：41 条 message + 8 个 tool 定义 = 20.8 KB
request bytes = 20850 ; segments=41 aux_strings=186 total detect units=227
detect-all ms: min=15.3 med=19.0 max=35.8
```

2000 字单次 1.5ms（和基线 §三 表 B 的 ≈2ms 同量级），20KB 的完整 agent 请求全量扫 19ms。**线性外推，200KB 的超长上下文约 190ms。** 而 LLM 调用本身是秒级——人类把额外延迟归咎于"工具"而不是"模型"的阈值我估计在 300~500ms。**规则层稳稳在预算内。** 所以"上个小模型"这个动作，买的是**开放词表召回**，不是速度；把"速度快"当成选型理由，是把因果搞反了。

**但规则层的召回天花板很低，而且我用自己的手确认了。** 我构造的测试文本里：

```
sample masked: 我叫〔人名·10fc4e6c〕，身份证 〔身份证·7b66a68a〕，手机号 〔手机号·f239d260〕，联系邮箱 〔邮箱·9950505d〕，户籍在海南省海口市美兰区。低保特困人员〔人名·10fc4e6c〕，现申请专项救助。
```

**"户籍在海南省海口市美兰区" 原样过去了。** 这独立复现了基线 §2.1 的"住址 ADDRESS 规则层完全不产出"和 §五.1 的"人名仅 4 条演示名词表"。看词表规模：`config/person_names.txt` 8 行（4 个名字 + 注释）、`classification_terms.txt` 9 行（6 词）、`sensitive_terms.txt` 32 行（约 20 个词）。**对政务数据来说，开放词表才是全部难度**——公民姓名不在这 4 个里，地址不在规则里，这是结构性的，不是调参能解决的。

**三个选项的诚实权衡：**

| | 召回 | 误报 | 延迟 | 可解释性 | 成熟度证据 |
|---|---|---|---|---|---|
| 纯规则 | 结构化号码满召回（基线 §2.1 micro 1.0000，618/618）；开放词表≈0 | 极低（基线：白名单 0/22 误报、难负例 26 条零满置信误判） | 19ms/20KB（我实测） | 逐条可查、可白名单、可审计 | 16/16 模块三族实测 |
| 快速小模型 | 理论高 | 未知，且**误报在无感形态下直接可见** | **我没测**（本机无 VT-x，Windows Server 2022） | 差——出了问题没法跟领导解释"模型认为这是敏感信息" | **几乎为零**：`recognizers/ner/adapter.py:29-31` `detect` 恒返回 `[]`；`semantic/judge.py` 的真 judge 路径按基线 §五.3 只做到"注入假后端的单元级验证" |
| 混合 | 高 | 中 | 看触发率 | 规则可解释、模型兜底 | 骨架已有：`judge.py:53-61` `from_env` 三项 env 齐备才启用、否则降级词表 |

**我倾向混合，但形态和人类可能设想的不同：模型不进主链，走影子路径。** 理由是成熟度证据的 stark contrast——规则层有三族实跑的 16/16，模型层只有一个恒返回空数组的适配器和一个假后端单测。**先让模型异步跑、只记"它本该拦住什么"，用这些日志反哺词表，跑上几千条真实流量、证明 precision/recall 净胜之后，再让它进主链去管一个窄触发面（比如姓氏启发式 0.5 置信命中的 ±200 字窗口）。** 这样"小模型"始终不背可用性的锅。

这里有个我觉得挺关键的点：**模型不需要看全文。** 规则层第一遍告诉我们"哪里值得看"，模型只看那几处窗口。这把 20KB 的一次调用变成 10×200 字（或者一个 batched 2KB 调用）——**这才是"速度快"的真实来源，是分片策略而不是模型尺寸。** 需求里"JEV 那种速度极快"的直觉我觉得抓错了抓手。

### 2.2 部署形态：不存在"同时覆盖"的那一个点

切入角让我深挖商业 agent，我梳理下来是：**浏览器的信任边界和 CLI 的信任边界是两个不同的对象**，这不是工具不够好，是物理上就是两件事。

- **本机透明代理（mitmproxy + 自建 CA + SNI 分流）**：能力最强，但 (a) CA 要写进机器信任库，Windows 上要管理员，会触发用户/IT 的警觉；(b) **HTTP/3(QUIC) 完全绕过 HTTP 代理**——走 QUIC 的 agent 我一个字节都看不到；(c) 部分 Electron 客户端有 pinning。
- **本地显式代理（`HTTP_PROXY`/`HTTPS_PROXY` 环境变量）**：拦截能力和上面一样，但**不碰机器信任库**（HTTPS 还是要 CA，但只在这个 shell 生命周期内）、一键可撤销。**我判断这是"投入产出比最高的第一形态"**——用户确实做了一件事，但那是一次性的、可文档化成一行命令的。对"无感"这个目标，它只差最后一步心理接受。
- **网关 API 模式（现状）**：零新工程。**关键 realization：很多"商业 agent"本来就支持自定义 endpoint + BYO key。** Claude Code、Cursor（BYO 模式）、Continue、Cline、Aider 这类都有 `--base-url` 或配置文件。**对这一类人，"对商业 agent 有效"这个诉求今天就已经满足了**——只是要改一行配置。真正做不到的是 SaaS 浏览器 agent（ChatGPT 网页版、Claude.ai、Gemini），它们没有可配 endpoint。
- **浏览器/IDE 插件**：单人成本最高（装、授权、看不见非浏览器流量），但是**对付证书固定的浏览器 agent 唯一不用 CA 的办法**。
- **SDK 封装**：只覆盖自己的代码，跟这个诉求无关。

所以我要说一句可能不太受欢迎的话：**"哪种拦截点能同时覆盖浏览器 SaaS agent 与本机 CLI agent"——答案是没有，而且追求这个答案是错的目标。** 正确的目标是把覆盖范围做得**可见**：一个面板告诉你哪些会话被处理了、以及哪些出口路径**没有**被看到。**静默的部分覆盖才是真正的产品风险**——一个用户以为自己的所有流量都被匿名了，而他的 IDE 插件绕过了代理，这比一个明知道自己只覆盖 CLI 的用户糟糕得多。**一个会诚实报告自己覆盖率的工具，比一个假装全覆盖的工具值钱。**

### 2.3 回写层：我认为最高价值的改动在这里

占位符在真实模型手里会被改形，这一点基线已经吃过教训了——`masking/mapper.py:49-65` 整段注释记录了反引号/空白/换行/全半角/易混字符/同形括号/**前缀段并入**，T8.4 为此把 `PLACEHOLDER_TOLERANT_MAX_LEN` 从 32 抬到 48，`remap.py:44` 与之同源。基线 §2.2 说 11 形态 + 4 负例全部钉死。

我照着这个思路自己加了几种它没列的形态去打，发现**三条真实泄漏**：

```
EN label (model translated)          -> LEAK  '〔ID_CARD·42197809〕'
6-hex hallucination                  -> LEAK  '〔身份证·dead〕'
brackets dropped entirely            -> LEAK  '身份证·42197809'
digest re-derived                    -> LEAK  '〔身份证·ecb312a3〕'
digest expanded to 16 hex            -> LEAK  '〔身份证·4219780942197809〕'
```

原因看代码很清楚：`canonical_placeholder`（`mapper.py:110-135`）在规范化后**标签原样保留**（spec §2.2 第 99 行"标签原样保留，不做任何归一——查表键即注册键"），标签是中文枚举（`recognizers/models.py:26-44`）。**模型被要求用英文回答时，它有充分理由把 `身份证` 翻译成 `ID_CARD`。** 这不是模型"乱来"，这是合理的语言行为，而我们的查表键不接受。

**我的建议是一个很小但很值钱的改动：让 digest 单独成为身份，标签降级为装饰。** 在 `SessionMapper.lookup` 旁边加一个按 `(ascii化标签, digest)` 的副索引，`〔ID_CARD·42197809〕` 和 `〔身份证·42197809〕` 就都能命中。digest 才是真正的身份，标签只是给模型看的提示。这样"标签翻译"这一类泄漏（我判断是商业 agent 场景下**最高频**的一类，因为用户的 agent 很可能配了英文 system prompt）从泄漏变成还原。**这是我这次思考里认为性价比最高的单点改动。**

更根本的一点我要说清楚：**你不可能让还原对一个不配合的模型 100% 可靠，所以目标不应该是"让还原更完整"，而应该是"让还原失败是安全的"。** 现在的失败行为是原样放行（`mapper.py:166-169`）——从泄漏角度是安全的（没有明文外泄），但从**用户可见性**角度是产品事故：用户会在答案里看到 `〔ID_CARD·42197809〕`，这直接违反"无感"。

而基线里**已经有一个正好能检出这件事的函数**：`tolerant_placeholder_hits`（`mapper.py:177-200`），spec §2.2 说它的定位就是"比 RESTORE_PATTERN 宽的泄漏检测面……真实大模型腿的『占位符零泄漏』断言以此为准"。**但它现在只被 eval 断言用，没有接任何运行时策略。** 我觉得这里应该接上第四种状态：检测到"形状可辨但查表未命中"的 token → 触发一次有界的补救（重问 / 改非流式整段还原 / 降级为原文重放），并计入指标。**没有这个，"还原失败"在生产环境里是一个静默的、用户会骂人的黑洞。**

至于"往商业 agent 的系统提示词里注入占位符规则"——我认为**不可靠，且不该作为正确性依赖**。四个理由：(a) 很多商业 agent 根本不给你注入的位置；(b) 给了也未必听，基线 §2.2 记录的改形是在**没有任何指示**的情况下发生的；(c) 长上下文 + 高温度下指令跟随本来就衰减；(d) **自指风险**——你注入的示例里如果带一个假身份证，你自己的规则层会把它当真的脱敏掉。我实测过检测面是全量的，这意味着你为保护自己而写的提示词会被自己脱敏。**结论：prompt 注入当作优化（把还原率从 90% 抬到 98%），绝不当作机制。** 正确性必须来自形状兜底 + 有界补救。

流式切块不用操心，`remap.py` 的 ≤48 有界缓冲 + 基线 §2.2 的 500 组 byte-exact fuzz 已经钉死。**但在无感形态下这个状态机要按协议重写一遍**——见 1.差异二，那才是成本所在。

### 2.4 性能预算："无感"是多少钱？

我的判断：不是 0ms，是"低到人不把这个延迟归咎于工具"。LLM 本身 1~10 秒，人的归咎阈值我估 300~500ms 附加延迟。

- 规则全链 2ms/1.2KB、19ms/20KB（我实测）→ 预算内，且余量大。
- 透明代理的 TLS 拦截 + 一跳 proxy：毫秒级，可忽略。
- 流式还原的 48 字符缓冲：只在流开头加几毫秒。
- **真正的延迟风险不是算力，是补救重试。** 如果 §2.3 说的第四种状态触发一次完整 LLM 重问，那是**秒级**的。所以补救必须稀有且有界（我倾向：同一会话内最多 1 次，且只对非流式整段还原做一次尝试）。**"让还原可靠"和"保持快"在这里是直接冲突的**，值得明说。

## 三、我认为最可能成功的路线

**路线 A（信心 0.8）：面向"支持自定义 endpoint 的商业 CLI agent"，加上对话指纹推导 session。**
理由：这是我唯一有把握说"缺的只是那一环"的路径。证据是实测的：稳定 session 下多轮一致（`coherence: STABLE`），现造 session 下崩（`coherence: BROKEN`），而我试的对话指纹（首个 user message 的 sha256 前 12 位）在多轮间稳定、不同对话不碰撞，形态 `sess_<12hex>` 正好落在 `SESSION_ID_RE` 的 `[A-Za-z0-9._-]{1,128}` 里、**不需要改任何校验规则**。剩下的全是已经跑通的东西。
我要主动说出它的软肋：指纹碰撞。政务场景里第一轮说"你好"是常事，两个用户会共享一个 session 命名空间。但我推了一下后果——碰撞只意味着两个无关用户的"张三"共用一个 token，因为 digest 是 `(session, type, normalized)` 三元组，值不同就不会互相覆盖，**所以这是频次分析意义上的弱交叉，不是内容泄漏**。**软肋是温和的，我认为可以带病上线。**

**证伪实验（先做这个，再写任何代码）**：拿本机现成的商业 CLI agent（AGENTS.md 里的 zcode / kimi 都可作样本）指向网关，跑一个 20 轮、含真实 PII 的对话，量三件事：(1) 跨轮占位符一致性；(2) 还原成功率；(3) 附加延迟。
**杀死标准：还原成功率 < 95% → 路线 A 死**，说明占位符方案本身不够好，先回去改占位符（§2.3 的标签副索引）再谈别的。

**路线 B（信心 0.5）：mitmproxy 透明代理，覆盖没有可配 endpoint 的那类 agent。**
价值高，风险集中在证书 pinning、QUIC、企业策略三件事上，`.zcode/plans/plan-sess_abea545a-*.md` §六 也已经把 pinning 列为已知风险。
**证伪实验**：在写任何 addon **之前**，先花一天测可达性——装 mitmproxy、装 CA、然后只看"哪些候选 agent 真的走了代理"。
**杀死标准：目标 agent 中honor 系统代理+信任库的 < 2 个 → 对这个产品不值得建**（对"IT 统管 CA 的政务内网"另一个故事可能仍值得，但那是完全不同的买方）。

**路线 C（信心 0.3）：快速决策小模型补开放词表召回。**
我把它排在最后，理由上面说了：成熟度证据最薄，且**我明确没有测过它的延迟**（本机 Windows Server 2022 无 VT-x，见 AGENTS.md 第一节）。如果非要做，走影子路径。

**如果只能做一件事**：不是 A 也不是 B，是**先补 §2.3 的标签副索引 + 把 `tolerant_placeholder_hits` 接成运行时策略**。因为它是唯一一条无论最终选哪种部署形态都需要的、且改动量在十行量级的改进。

## 四、风险、我不知道的、要人类拍板的

**风险（按我的排序）**

1. **静默的部分覆盖。** §2.2 说的。用户以为全覆盖、实际某条出口没被看到，比诚实的部分覆盖更危险。
2. **映射表落到终端机器上。** 基线 §六.6 的明文 `session_map.db`，在无感形态下从"内网受控库的残余风险"变成"个人笔记本上的明文索引文件"。**这是合规问题不是技术问题。**
3. **拦截无法无感。** §1.差异四那个三角。
4. **演示级词表就是产品的真实水平。** 基线 §六.9 自己写了密级 6 词、人名 4 个。对真实政务用户，召回会难看until 有人去整理词表。**这是一个伪装成技术问题的数据问题，也是最可能让试点失败的东西。**
5. **移动的靶子。** 我这次 `git status` 确认还是 36 个未提交文件、HEAD 还是 `d6daffd`，与基线 §七.1 一致；但基线 §七.3 说 2026-10-04 03:0x 还有一轮 gate_final 在跑。**我这份思考描述的是一个还在动的快照。**

**我不知道的（不猜）**

- 目标商业 agent 是否 pinning / 是否走 QUIC。我**没有**本机可测的这类 agent：`pip list | grep -i "mitm\|proxy"` 无结果，仓内 `pyproject.toml` 依赖里也没有 mitmproxy（`constraints.txt` 57 行我通读过），`.zcode/plans/` 里 qoder/workbuddy 写作"可装则装"、状态未验证。**这一项我没有做任何实测。**
- 小模型在本机的真实 CPU 延迟。**我没测，也不打算猜。**
- 目标客户能不能/愿不愿意在自己机器上装 CA。政策问题。
- "无感"是否包含审计看板，还是只指管道。
- `tolerant_placeholder_hits` 接成运行时策略后，补救重试的次数上限该定多少——这个数取决于真实还原成功率分布，而我手上没有分布。

**要人类拍板的分叉（按重要性）**

1. **买方是"政务内网 IT 统管"还是"公务员自带电脑"？** 这是最大的分叉，而且我觉得**人类口头说的是后者（"对商业 agent 也有效"暗示用户自己装），但基线现在的形态明显是前者（部门 Key、三部门、政务云腿）。** 这两个是完全不同的产品，形态、CA 策略、映射表位置、合规叙事全都不一样。**我不认为我该替人类选。**
2. 命中密级时给用户看什么？拦截的可见性怎么设计？
3. 目标商业 agent 的具体名单。我没有名单就设计不出 `--allow_hosts` 的白名单。
4. 映射表是否 at-rest 加密，谁来承担这个密钥。
5. 覆盖率要不要对用户诚实披露（我强烈建议要，但这是产品决策）。
