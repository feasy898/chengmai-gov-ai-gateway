## 一、"测过了"意味着什么：从 a–h 决策反推必须钉死的行为

我不打算用"功能清单"定义测过，而是逐条问：**这条架构裁决如果被实现错了，用户会看到什么？那个"看到"能不能变成一条断言？** 能，才算被测试钉住。

### a 部署形态（T1 回环为主 / T2 显式代理 / T3 押后）

**a 的真正测试面不是"代理能不能转发"，而是"代理对用户环境改了多少东西"**。理由：人类意图里的"用户无感"【规划§一.1】，在回环形态下极易退化成"用户无感地改变了系统状态"。所以必须钉住：

- **注入恒定性**：壳注入的 `x-anongw-session-id` 在连续 N 个请求里必须逐字相同。**反例断言要写死**：若有人把壳改成每请求现造会话（基线 `gateway/app.py:385-389` 就是这个行为），同值占位符会逐轮漂移，而所有功能测试仍然全绿——只有"恒定性"这一条会红。这是【规划§三b】"值级键经壳恒定注入实例会话号达成"的**唯一可测表达**。
- **环境零污染**：T2 形态按运行时 CA 变量分发（`REQUESTS_CA_BUNDLE`/`SSL_CERT_FILE`/`NODE_EXTRA_CA_CERTS`），**不写系统信任库**【规划§三a】。可测：安装前后对 Windows 证书库做快照（`certutil -store My` 的输出哈希）比对，断言未变。卸载 = 一键可撤销【规划四M5】，同一条断言反向再跑一次。
- **未覆盖出口必须可见**：R2 静默部分覆盖是首要风险【规划§五R2】。测试上，"不覆盖"没法靠断言测出来，只能靠**清单对照**：矩阵里登记的 agent 台数 vs 面板里报告的被处理会话数 vs E1 矩阵里声明的不覆盖项，三者必须能对账，且对不上时测试要红。

### b 值级键（值级/安装实例级）

- 正向：同值跨会话、跨进程、跨重启**恒同**【规划§三b】——三条分别对应 M1-#1、M3 验收第 1 条。
- **必须写死的隐私让步**【规划§三b 遗留 / 5.2-F2】：值级键意味着"同一个人在同一台机器上，所有会话里的占位符恒同"，跨会话可关联是**主动让渡的属性**。我的主张是：不要"不测它"，而是**写一条断言把让渡钉死**（断言 A：任意两个不同 session_id 下同值占位符相同）。这样将来若要改回会话级，必须改测试而不是改文档——决策落在代码里而不是落在散文里。
- 负向（易漏）：换 MASK_KEY 或换实例 id 之后，**旧占位符绝不可被误还原成错误值**。现有 `restore_tolerant` 以查表命中为终审闸（`masking/mapper.py:161-164`），理论上有保证，但要有负例钉住——这是"错还原比不还原危险得多"的场景。

### c 判定层（规则为主、模型只当识别器、v1 不进主链）

- 新工具侧真正的新增断言不是"规则召回 1.0000"（那是基线的），而是：**从一个真实商业 agent 抓下来的请求形状里，上游实收字节级零原值**。理由：请求侧检测面 `_aux_texts` 结构无关（`gateway/pipeline.py:195-239`），这在基线是"白送"，但在无感形态下请求是 agent 自己拼的，形状不受我们控制——这条才是真风险。
- M4 若立项，"30ms 硬预算超限即降级回规则，绝不阻塞主链"【规划§三c】必须有一条**可注入**的测试路径（人为把模型延迟拉爆），否则降级路径永远没被执行过。

### d 协议面（v1 只 OpenAI，M2 加 Anthropic）

- Anthropic 的 `tool_use`/`input_json_delta` 必须**沿用 toolbuf 的 hold-to-finish**（`masking/toolbuf.py` 对应 `evals/m3_masking.py:370-391` 的单 delta 整体还原断言）。理由：逐 delta 还原会把 JSON 打断——这是 OpenAI 资产迁移到 Anthropic 时最容易丢、且丢了之后**功能测试也可能绿**（只有工具调用那条会红）的一条。我主张把"工具参数 JSON 可解析 + 占位符零残留"作为 Anthropic 适配器的**必测项**而非可选项。
- **适配器隔离负例**：拿 OpenAI 还原器跑 Anthropic 载荷，必须零改写。这条测的是"三处薄壳抽成协议适配器接口"【规划§三d】是否真的隔离干净，而不是靠正例通过来推断。

### e 性能预算（TTFT 增量 p50≤20ms / p95≤50ms）

见 §五。核心判断：**"无感"在测试里唯一可操作的定义是"差值"，不是绝对值**。

## 二、开发者可见测试 vs holdout：边界怎么划

我用的判据很简单：**一条用例一旦被开发者读到，它还能不能区分"实现了"和"迎合了这条用例"？** 能区分 → 开发者可见；不能 → holdout。

### 必须 holdout 的（读过就会"应试"）

1. **对抗性占位符改写集**【HOLDOUT，必须移出开发者可见范围】：具体的改形形态清单（哪种括号变体、哪种全半角、哪种类模型最常拆哪一类）。基线把形态目录写死在 `evals/t0_stream.py:620-647` 和 `evals/m3_masking.py:255-274`——**这对基线是正确的**（它测的是"我们声称支持这些形态"），但对无感形态是错的：开发者只要照着这 20 来形态把 `canonical_placeholder` 调宽，测试就全绿，而真实模型的改形分布远不止这些。holdout 版必须由**实测采集**而非人工枚举。
2. **真实语料分布的召回/误报集**【HOLDOUT】：【规划§二缺口4】已经用 1792 个 expected 实体量出规则层 39.8% 不可检出。如果这个分布以逐条用例形式给开发者，就会写出"针对 39.8% 里每一类补一条正则"的实现——合成语料上的高分、生产上撒谎（【规划§三c】引 M3 §2.1 的原话）。holdout 应以**分布统计**形态存在（多少比例、哪一类），不逐条给。
3. **未见过 agent/协议变体**【HOLDOUT】：矩阵里每个 agent 的具体 quirk（比如某个 agent 会把 system 放 `instructions`、某个会在 tool_calls 里回传历史密级）。E1 矩阵是**给 owner 和 PM 看的**，不该整份进开发者可见测试——否则实现会按名单特判。
4. **多轮漂移的构造配方**【HOLDOUT】：不是"第 5 轮要稳"这种断言，而是"怎样制造漂移"（历史压缩的形状、指纹漂移触发条件）。

### 可以开发者可见的

- 全部**机制性**断言：恒定注入、转发保真、流式中继、工具参数 JSON 可解析、审计零明文、DPAPI 负例、并发零串扰。这些的正确答案就是契约本身，开发者看见不损失信息。
- 全部**负例**（误替、误还原、pinning 不绕过、静默拦截禁令）。
- 仪器校准集本身（见 §四）——我认为这一条**故意留在开发者可见**，因为仪器有盲区是必须让开发者知道的结构性事实，藏起来只会让所有泄漏断言一起假绿。藏的应该是"我们没测过的形态"，不是"我们测了但仪器看不见"。

### 我这里的一个开放问题

holdout 的**执行权**归谁？如果 holdout 只在交付前跑一次，它测的是"发布那一刻的泛化"；如果每次提交都跑，它会变成"另一个开发者在维护的测试"。【规划§五R3】说 agent 行为会漂移、矩阵要每版本回归——我倾向 holdout 由独立方按固定 cadence（每里程碑 + 每季度）跑并**只发布聚合数字不发布用例**，但这条是流程决策，不是测试设计能单方面定的。

## 四、对抗与安全用例：本会话实测出来的核心发现

### 4.1 泄漏判据存在**互补盲区**，且现有验收口径是乐观下界

【跑过】我构造 6 种改形，同一批数据问两个判据：

| 改形形态 | `tolerant_placeholder_hits`（形状检测器） | 映射 digest 反查 oracle |
|---|---|---|
| 16-hex 扩展（digest 被补到 16 位） | **0（漏）** | 1（抓到 `f8808372f880`） |
| 括号被剥除（裸 `手机号·f8808372`） | **0（漏）** | 1 |
| 裸 hex（连标签都没有） | **0（漏）** | 1 |
| 表格拆分（label 与 digest 分处两格） | **0（漏）** | 1 |
| digest 被改写/幻觉（hex 换值） | 1（抓到） | **0（漏）** |
| 正常公文（无误报对照） | 0 | 0 |

**这意味着什么**：两者**互不包含**，各自的盲区正好互补。最要命的前三种（含表格拆分）——**既不可还原、也不可检测**，用户在屏幕上看到裸 `f8808372` 或 `〔手机号·f8808372f880〕`，而运行时计数器报告 0。

**为什么没人早发现**：`restore_tolerant` 和 `tolerant_placeholder_hits` **共用同一个判定链**（`masking/mapper.py:159` 与 `:194` 都调 `canonical_placeholder`）。仪器与被测物同源 ⇒ **同源盲区不可能被仪器自己发现**。这不是实现 bug，是**仪器校准缺失**。

**因此我对 §1.2-#2 的异议**：【规划§1.2-#2】把"占位符残留率 ≤2%"的计量仪器定为修补后的 `tolerant_placeholder_hits`【规划§三g】。我实测的证据表明：即使按规划把"裸 digest 检测面"那条补丁做了【规划§三g 补丁 2】，表格拆分与 16-hex 扩展**仍然在盲区里**（补丁 2 只加"裸 `标签·hex8-12`"，覆盖不了表格拆分，也覆盖不了 16-hex——它会被 `hex8-12` 的长度上限挡掉）。所以：
- **残留率必须按并集口径计量**：`形状检测器 ∪ 映射 digest 反查 oracle`。两者都要求的那个集合才叫泄漏。
- **并集口径下 ≤2% 大概率不达标**，因为【规划§三g】已经把"结构级重组"承认为"正则原理上不可救的残余风险"。这直接连到 5.2-F6（占位符形态 bake-off）——**残留率的分母里要不要含不可救形态，是一个必须 owner 拍的口径问题**，不是测试能单方面定的。我倾向：**按形态分桶报告，整体数字只作为披露不作门禁，门禁只卡"可救形态"的存活率**。理由：用一个已知不可救的形态去卡门，等于逼着开发去写 hack。

### 4.2 我要加的第一个测试组：仪器校准（`t_leak/test_detector_calibration.py`）

它测的不是功能，是**检测器自己**：每个"已知会泄漏到屏幕"的形态，必须至少被一个判据抓到；每个"普通文本"必须两个判据都零误报。这条测试**故意留在开发者可见**（理由见 §二）。它的价值：它会把 §4.1 的表格变成 CI 里会红的东西。

### 4.3 三类"还原失败"必须分开记账

我建议 E2 的每轮记录四列而不是两列：`(形态, 是否还原成功, 是否被检测器看见, 是否真的到达用户屏幕)`。因为这三件事的失败模式完全不同：
- 不可还原但可见 → 用户看到 `〔手机号·a1b2c3d4〕`，至少知道自己出了事（治理上可接受）。
- 不可还原且不可见 → 用户看到 `f8808372`，以为系统坏了（产品级失败）。
- 可还原但检测器误报 → 只是计数虚高，可接受。

【规划§一.2-#5】"不骗人"原则落到测试上就是这个：**面板上的泄漏计数必须来自并集口径，且必须能被复算**。

### 4.4 模型"补全"或幻觉出原值怎么办

分两种，测试方向完全相反：
- **补全占位符**（把 hex 补长、把标签补成别的）→ 属于 4.1 的改形集，测"能否还原/能否被检测"。
- **凭空幻觉出结构化实体**（模型自己编了一个看起来像身份证的串）：它**不是泄漏**（上游从没收到过这个值），也不是占位符残留（形状不对）。v1 的正确姿态是：**只计数、不阻断**，把"响应侧出现的、映射表外的结构化实体"计入审计与可见提示。这正是【规划§三c】里 M4 可选项"输出侧残差验证器"的用武之地——所以我主张 M4 的这组测试现在就要**先把计数口径设计好**（哪怕 v1 不实现），否则将来接了模型没有基线数字。
  **理由**：这类"数据可信度"问题在 v1 是**已知不可测**（模型行为不受我们控制）。测试能做的只有两件：①确认它不会被误当成泄漏而污染泄漏率指标；②确认它出现时有痕迹。写"断言它不发生"的测试等于写一条必然 flaky 的测试。

### 4.5 翻译 / 表格 / 摘要重组

【规划§三g】已承认为不可救。我的立场：**不要试图测"能还原"**，要把它变成**已知残留率的分桶**。E2 的杀死线（<95% 触发重审）【规划§四E2】必须**分形态给线**：可救形态（改形类）卡 95%，不可救形态（结构重组类）只记录不卡门。整体数字若直接卡 95%，我判断会被"用注入提示词刷分"这种优化手段糊过去。

## 五、性能与无感：怎么测才不抖

### 5.1 先纠正一个事实：基线没有 p95 基础设施

【跑过】grep：`GATEWAY_OVERHEAD_P95_MS = 150`（`evals/thresholds.py:8`）**除定义行外全仓零引用**；`m2_recognizers.py:266-274` 与 `m2_semantic.py:422` 用的是"10 次均值"。所以【规划§三e】的 p50/p95 预算**没有任何现成测量代码可复用**，测试文档必须自己建，且不能假装"沿用基线口径"。

### 5.2 唯一能在 CI 里不抖的测法：**差值法**

- 测**绝对 TTFT** 是不可能测的：LLM 自身 TTFT 数百 ms 起【规划§三e】，20ms 的预算是它的 5% 量级，信噪比极低。
- 所以：**同一请求体 bytes、同一个本地 mock 上游，跑两遍**——A 直通 mock（基线），B 经壳，断言 `p50(B) − p50(A) ≤ 20ms`、`p95(B) − p95(A) ≤ 50ms`。上游固定成 mock 是关键：它把上游方差完全消掉，剩下的才是壳的开销。
- 抖动控制清单（我建议写进测试文档当硬约定）：预热 ≥20 次丢弃；请求体 bytes 固定不变（不重新生成，避免 JSON 序列化差）；单线程；样本 ≥50；**p50 卡硬门、p95 只 WARN + 离线归档趋势**。最后一条的理由：n=50 时 p95 的置信区间极宽（本质是第 3 个最慢样本），卡门等于制造随机失败。p95 的门放在**专门的 perf 批**（独占机、禁并行——【基线§六#17】端口独占纪律同样适用于此），不进 CI 主线。

### 5.3 流式"无感"的断言

【规划§三e】的"不引入基线语义之外的新增用户可见缓冲"是可测的，而且**有现成的仪器**：`StreamRestorer` 的候选缓冲上界 `MAX_PLACEHOLDER_LEN = 48`（`masking/remap.py:44`，与 `mapper.py:78` 同源），且是"命中即冲刷"。测法：逐 chunk 记到达时间戳，断言**任何一次冲刷的延迟 ≤ 48 字符对应的时间**，且整段流的总时长与直通 mock 的差 ≤ 预算。这比"断言输出字节相同"更能反映用户体感的无感——字节相同但全部等 flush 才吐，就是有感的。

### 5.4 大上下文与超线性

【规划§二缺口7】记 49,800 字/3000 实体 **417ms**，且 `recognizers/rule/detect.py:340` 的 `_overlaps` 是 `any(...)` 线性扫描（我读过该函数，确认是 O(k²) 的来源之一）。E5 原型未落地前，"大上下文无感"**判定不成立**。测试上：E5 原型前后各跑同一夹具，p95 ≤100ms【规划§三e】作为 M2 的门。这个断言与 §5.2 的抖动控制不同——417ms vs 100ms 有 4 倍余量，可以直接卡硬门。
