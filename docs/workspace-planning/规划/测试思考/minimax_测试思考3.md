## 0. 我是怎么开始想的

### 0.1 先问一句：这个工具「测过了」是什么意思

我一开始按模块列功能点：脱敏测一下、还原测一下、性能测一下。写到一半觉得不对——**那是覆盖率，不是可判定的失败**。测试的价值在于"**它能不能在被产品做错的时候变红**"，判据收敛成一句：

> 一条用例算不算数，看它失败时能不能指认一个**用户会遭遇的具体伤害**。指认不出来的，是覆盖率幻觉。

按这个判据回看，规划 §1.2 的六条验收句是六类伤害的抽象；而 §三 的 a–h 八个决策是**伤害的成因开关**——每个决策落死都必然打开一类新失败面、关掉一类旧失败面。这才是起点。

## 1. 从 a–h 逐条推导「必须被钉住的行为」

### a 部署形态（T1 回环直配 / T2 wrapper+env 代理 / T3 押后）

形态不是"部署细节"，它决定**流量怎么到工具手里**。测的不是"代理能不能转发"，而是两条可证伪命题：
- **入站式**：凡进入壳的请求，出站文本必过识别层。落在 `_aux_texts`（`gateway/pipeline.py:195`，`include_keys=True` 三处调用在 `:220/:231/:238`）——键名、多模态非 text 段、`tools`、`history tool_calls`、`system`/`instructions` 全在面内。M1 实测已证 `instructions`/`system` 命中（§2.1），**这条要抄成壳级断言，不能只当引擎事实引用**。
- **出站式（更关键，也最易漏）**：凡是**没进壳**的出口，工具不得声称覆盖。§1.2-#5 把它写成"不骗人"的一等验收句却没给测试形态。建议做成**差分观察用例**：同一 agent、同一 prompt，开/关工具各抓一次出网目的地集合，`断言 = (开着时未见的目的地) == (关闭时可见的目的地) - 显式白名单`（QUIC/DoH/pinning 命中）。它的价值在于**会随商业 agent 升级自动变红**——R3 风险（§5.1）由此兜底，而不是靠人记得去测。

### b 值级键（安装实例级）

四个断言方向，用 §0.2-3 的实测钉死：
1. 同值跨**进程/跨重启/跨会话**恒同（值级生效）；
2. 换安装实例 → 异（补偿控制，对应 F2）；
3. 归一化等价仍成立（`138 0013 8000` 与 `13800138000` 同占位符，基线 §2.2 口径）；
4. **可链接性是设计意图**，需要一个"反向断言"钉住它：某次重构若偷偷把 instance_id 换回每请求 id，**必须**有一条红。

这里要**自我修正**一个可能的误读：§三 b 说"基线 m3『跨会话互异』断言继续在网关形态成立"是对的，但容易被读成"m3 要改"。实际不需要改——`evals/m3_masking.py:115` 直接构造 `SessionMapper(f"sess_m3_cross_{k}", ...)`，绕开壳，**引擎层那 9 项一条都不会因决策 b 而失败**。失效的不是断言，是断言对产品的**描述力**。正确动作是"m3 原样保留 + 新增壳级相反断言"；写成后者会制造不必要的回归噪音。

b 决策还顺手关掉一个失败面：**会话漂移**（历史压缩、指纹漂移）在值级键下结构性消失，`gateway/app.py:384-390` 缺头现造会话的路径（§2.2-#2）在壳形态下不再被触发。对应一条**负向断言**：壳注入的 session 头在任何请求路径上都是同一常量（不是"看起来一样"，是 `assert header == instance_id` 逐字节）。

### c 判定层（规则为主，模型只当识别器，v1 不进主链）

v1 能测的不是模型质量，是**级联触发判据是纯函数**。M4 若立项，"规则未命中 且 文本像自然语言"这个判定必须在不加载任何模型时可单测（建议抽成 `cascade_should_invoke(text, rule_findings) -> bool` 并写纯函数用例）。v1 阶段另加两条**降级不变式**：模型不可用时主链行为与 rules-only 完全一致（M4 的 30ms 硬预算降级路径，接口现在就留出来测）。

### d 协议面（v1 OpenAI，M2 Anthropic）

请求侧"白送"是结论，不是免测。Anthropic 的 `system`（字符串或 `[{type:text}]` 块数组）、`messages[].content` 块数组、`tools[].input_schema` 里的示例值、`tool_use.input`——每条都要在检测面内各有一条断言。**块数组**尤其要测：`_iter_string_leaves` 递归叶子能覆盖，但没人钉过 `content: [{type:"text",text:"..."}]` 这个具体形状。

响应侧分两档断言，我把一开始的"byte-exact 透传"改掉了（**修正**）：SSE 规范允许一个事件写成多行 `data:`，而 `iter_sse_data_lines` 会用 `\n` 拼成一条（`gateway/sse.py:81-86`），重帧时"一行还是多行"是实现选择，不该被 byte 级断言锁死。故：
- **A 档（无占位符事件）**：**byte-exact**。这类事件壳一个字节都不该碰，是最便宜最强的不变式。§0.2-2 实测说明这条**现在是破的**（`event:` 丢失）——M2 的第一个红应该是它。
- **B 档（含占位符事件）**：断言"**解析后事件序列相等**"（`[event_name, payload]` 逐项相等）+ 占位符零残留 + 顺序不变；byte 级只在"单行 data"子情形下额外加严。

另需单独覆盖的 Anthropic 面：`content_block_start`/`_stop`、`message_delta`（`stop_reason`）、`message_stop`、多 `content_block` 交错、`thinking_delta`、`input_json_delta`（工具参数走 hold-to-finish 还是就地还原，是**契约决策**，测试要先把这个决策逼出来再写断言）、以及 **event 名与 `data.type` 不一致**的畸形输入（我倾向：按 `data.type` 走、日志告警、不静默）。

### e 性能预算 / f 透传退化 / g 泄漏计量 / h 引擎双接法

- **e**：见 §5。
- **f**：透传形态不做路由（§三 f），故要一条**不可达断言**：T2/T3 形态下三路由矩阵**不可被调用**（防有人顺手接回）。密级命中必须**有感**：优先本地代答且**按目标协议合成正确形状**（Anthropic 客户端收到 OpenAI 形状错误体是新的失败面），代答不可行才 403，两种都断言**上游零触达**（沿用基线 §2.3 的 `BLOCK 恒 null` 口径）。
- **g**：见 §0.2-1 与 §4。
- **h**：M1 转发 vs M2 进程内，**行为等价性**是这条决策的验收本体：同一夹具两条路径，输出归一化后等价（流式按"客户端拼接结果"等价，非流式按"字段集"等价）。建议从 M1 第一版壳就写骨架（哪怕 M1 永远只跑转发腿），否则 M2 收敛接法时没有对照基。

## 2. 分层：开发者可见 vs holdout，边界划在哪

### 2.1 判据

不是"敏感用例放 holdout"（本案没有密钥型敏感），而是**过拟合可达性**：

> 如果开发者读过这条用例，他能否通过特判/硬编码让它变绿，而产品能力毫无真实提升？

按此判据过一遍基线资产，结论有点扎人：**基线里最"扎实"的改形测试（`evals/m3_masking.py:255-274` 的 15 种 forms，每种还跑 2 个流式切块），恰好是最容易过拟合的那一类**。它是字面清单；开发者照着 `canonical_placeholder`（`masking/mapper.py:110-135`）加 15 个分支，forms 全绿，而真实模型的下一种改形照样挂。这不是假设——M2 实测的 5 种改形泄漏（§2.2-#5）本来就不在这 15 种里。**清单型测试钉的是"已知的错"，不是"会犯的错"。**

### 2.2 holdout 必须覆盖的五类泛化面

| 面 | 用什么未被开发者见到的材料 | 断言形态 |
|---|---|---|
| **真实语料分布** | owner 授权的 20–50 份政务文本（F7）；**不能**是 `m8_generator` 产的合成集 | 召回/精确率按真实分布重算（规划 §2.2-#4 已量到合成集 39.8% 不可检出，真实分布只会更差） |
| **未见的 agent/协议变体** | 未在 E1 矩阵里的 agent；ping/error/`message_delta`/多 content block/event 名与 type 不一致 | A/B/C 分级（见 §4） |
| **对抗性占位符改写** | 开发者没见过的改形**算子**（见下） | 分级断言 |
| **长上下文** | 50k 字夹具中占位符出现在首/中/尾；跨 30 轮引用 | 还原率不随位置/距离衰减；E5 修复后 p95 ≤ 100ms |
| **多轮漂移** | 历史压缩后再引用；agent 把占位符复述成自然语言 | 区分"零占位符残留"与"信息保真"（见 §4 的最后一格） |

**holdout 语料生成的一个隐蔽泄漏通道（我差点漏掉）**：若 holdout 语料由仓内可见的 `benchmark` 生成器 + 公开 seed 产出（基线 §三 表 B：seed 20260928，372 用例双跑字节一致），开发者只要读生成器参数就能**重演 holdout**——形式上 holdout、实质上 dev 可见。故 holdout 语料必须自带生成器或用真实文本。

对抗性改形算子（holdout 专用，我自己也还没穷尽）：hex 插零宽字符；label 繁体化（`手机号`→`手機號`，NFKC 不归一的一类，**我怀疑仪器与还原双双漏，标为待验**）；hex 截到 7 位；hex 补 0 到 16 位（已实测仪器漏）；嵌套括号；占位符整体落进 code fence / 行内 code / 表格单元格 / 引用块 / 链接标题 / HTML 注释。**后几个不是"改形"是"重组"**，处置规则不同（§4）。

### 2.3 holdout 的执行纪律

- holdout 代码**不进开发者仓**（物理隔离目录 + 独立 runner）：开发者能看到"有一条 holdout 红了"，看不到红在哪。
- 报告只回传**聚合数字 + 失败形态分类标签**（如"表格拆分 3 例"），不回传具体输入——第一次失败之后 holdout 就部分失效了。
- **holdout 必须在对应功能实现之前写第一版**。这是本文最强的排序意见：排在开发后面写，它就退化成"针对已有实现补测试"，测的是"实现碰巧对不对"而非"能力泛不泛化"。故它应紧跟最小回路 `t1_roundtrip` 之后、M1 迭代开始之前。
- 缺口如实登记：`:9004` 真实腿是单点（基线 §六#16），holdout 若依赖它，掉线判 DEFERRED 而非 PASS（照搬 m10_e2e 的三态惯例）。

## 4. 对抗与安全用例：把"伤害"写成断言

### 4.1 存活的分母口径（需要拍板的开放问题）

规划 §四 E2 说"≥200 轮逼模型回显，统计改形率/救回率/泄漏率"，但**分母没定义**。一个请求里有 N 个占位符、模型只复述 M 个，存活率可以是 `M/N`（占位符单位）或 `M/M'`（提及单位），两者能差出一倍。我倾向前者——**用户视角是"屏幕上还剩几个占位符"**——但这是口径问题，不该由测试文档单方面定，应在 §六 验收对照里显式列为待 owner 确认。

### 4.2 重组/翻译/摘要：把不可修的失败改成"必须被看见的失败"

这是本文我最想强调的一条测试原则。

- **结构级重组**（label 与 digest 拆进表格不同单元格）：§三 g 已裁定正则原理上不可救。**那它就不该是一条 FAIL 断言**，而是一条"**必须被计量**"的断言：
  > `assert 表格拆分数 == T6 泄漏计数器读数`
  > 即：E2 跑出表格拆分而 T6 计数器为 0 时，**T6 才是 bug**，不是 E2。这叫"失败必须可见"——把一个修不了的失败，转成"**漏报它就是缺陷**"的失败。用例于是从"要求系统做不到的事"变成"要求系统诚实"，后者才可能长期为绿。
- **翻译（EN label）**：§0.2-1 实测检测面能看见、还原面查表 miss → 标签副索引的**正面验收**。此时用例可可见（对应一个已裁定补丁），但 **holdout 侧另备未裁定的翻译形态**。
- **摘要**：模型把占位符换成"该身份证对应的申请人"——**零占位符残留，但信息丢了**。所以"用户可见占位符残留率"**测不出信息损失**，必须补一格**语义保真**。建议 holdout 里做人工盲评（n≈50/轮、双人、报 κ），量"用户是否察觉内容变弱/变空"。这是唯一能钉住"**用户无感**"原话的手段——无感的本质是"用户没觉得少了东西"，任何自动代理指标都测不到。

### 4.3 幻觉与错还原：宁可泄漏，绝不错还原

模型把 8 位 hex 补成 16 位、或幻觉出 `〔人名·deadbeef〕`。当前仪器对前者**漏报**（§0.2-1 实测），补丁后必须能报——这是一条仪器断言。

更危险的方向是反的：`〔人名·deadbeef〕` 若命中映射表里**别人的**条目，就把 A 的身份显示给了 B。`mapper.py:161` 的"查表命中终审闸"正是防这个（`restore_tolerant` 在 `masking/mapper.py:160-165` 命中才替换），`m3_masking.py:288-292` 的 6 条负例也在钉它。建议**升格为一等验收**，措辞要硬：

> **错还原率 ≡ 0 恒成立，即使代价是漏还原。** §5.2-F5 已有"原样放行不还原错人"的口径，测试文档应写成不可协商的断言族（所有未知形状、所有查表未命中、所有幻觉 hex 形态 → 恒原样放行）。

### 4.4 渗漏可见性（MM1 的渗漏面）怎么变成断言

泄漏检测不能只扫最终 stdout。要扫的面（每面一条断言）：①客户端最终收到的**字节**（流式拼接后 / 非流式整段）；②agent 进程的 stdout/stderr；③agent **写盘**的会话历史与日志——商业 agent 普遍落盘，这是最易漏的一面；④托盘/提示文案（§三 f 的"显式可见"文案本身不得含占位符）；⑤审计库 + 映射库（沿用 m7 的 bytes 级扫描口径）；⑥**测试自身的日志**——eval 在失败信息里打印原值，CI 日志就成了新渗漏面（与基线 §六#6 同类风险在测试面重现），建议用一条"失败输出不得含原值"的元断言钉住，成本极低。

## 5. 性能与无感：怎么测才不抖

### 5.1 先摆事实：规划里的预算按现有证据是可抖的

规划 §三 e 的请求侧预算是 **p50 ≤ 20ms / p95 ≤ 50ms**，而同一节引的实测是"规则全链 **19ms**/20KB（M1）"。**证据是 19，线是 20，余量 1ms。** 这种断言放进 CI 必然 flake，而 flake 的真正危害不是"偶尔红"，是**团队学会忽略红灯**——真正的性能回归被一起忽略。

基线自己已写明：全部毫秒值是**单机单次实测**，只作"远低于阈值"的佐证、**不作稳定指标**（基线 §三 表 B 注）。测试文档若把 `19ms`/`2ms`/`0.26ms` 写成阈值就是**自相矛盾**——建议明令禁止。

### 5.2 三档分离（我的核心主张）

| 档 | 何时跑 | 断言什么 | 为什么这样切 |
|---|---|---|---|
| **功能门** | 每次提交 | 只测"20KB 请求被正确处理、输出正确" | 时间断言进功能门 = 制造 flake = 教人忽略红灯 |
| **基准门** | 每日 / 手动，专用机、不并行 | **报分布**（p50/p95/p99/max + 机器状态），断言**相对基线的回归比**（如 `p95 ≤ 基线p95 × 1.5`，且 `基线p95 ≤ 0.5 × 预算` 以防测量代码本身坏了导致基线虚高） | 绝对值会随机器/电源/后台漂；相对值抗环境 |
| **预算门** | 发版前，一次性 | n ≥ 200 次取 p50/p95 对照 §三 e；**不过就记录，不重跑到过** | 重跑到过 = 掩盖问题 |

### 5.3 降噪手段（部分由我 §0.2-4 的实测反推）

- **预热后取样**：我实测批间 p50 为 0.365 / 0.360 / 0.295 ms，**前两批明显慢于第三批**（约 24%），丢弃前 N 次后 p50 收窄。这是本机实测，不是抄来的经验。
- **分位数用最近邻**（`sorted[n]`）而非插值；**n ≥ 200** 才谈得上稳的 p95（n=50 时 p95 就是最大值；我实测 400 次的 p99=0.4345 与 max=0.4768 只差 0.04ms，n 再小尾部全是噪声）。
- `time.perf_counter`；关后台、固定电源计划；必要时绑核。
- **上游用可脚本化 mock**：TTFT 增量必须**差分测量**——同一请求分别走「壳+网关」与「直连 mock 上游」，量首字节时间之差，mock 首字节延迟脚本化为常量。**不要用真实腿做主口径**（基线 §六#16 隧道单点 + 真实模型 TTFT 数百 ms 起，噪声完全盖过 20ms 的信号），真实腿只做一次性确认。
- **阈值一处可调**：沿用 `evals/thresholds.py:3-4` 的纪律（"禁止在用例里散落魔法数字"），新工具另起壳专属 thresholds。
- **大上下文另算**：50k 字 p95 ≤ 100ms（E5 修复后）独立成档，别和 20KB 预算混算。
- **流式还原不测时间，测不变式**：§三 e 说"不引入基线语义外的新增用户可见缓冲"。正确测法是**缓冲长度**（`pending_len ≤ MAX_PLACEHOLDER_LEN`，`masking/remap.py:44`，基线已钉 ≤48）+ **首字节不被吞**：注入含占位符的回复，断言客户端在收到第一个非占位符 token 前不被额外阻塞。测时间易抖，测缓冲与顺序不会。
